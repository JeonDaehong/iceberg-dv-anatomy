Apache Iceberg V3 · 읽기 경로 해부

Deletion Vector Anatomy

행마다 삭제 여부를 묻는 루프가 스캔 CPU 의 절반을 먹는다. 그걸 찾고, 고치고, 내 노트북 밖에서도 성립하는지 확인한 기록 — 틀렸던 것까지 포함해서.

발견 44개 측정 축 28개 빗나간 예측 15개 Spark 4.0.4 · Iceberg 1.11.0 최종 2026-09-08
Apache Iceberg V3 의 deletion vector 읽기 경로를 뜯어 문제를 찾고, 고치고, 그 결과가 내 노트북 밖에서도 성립하는지 확인한 기록. 이 문서는 서사다. 40개의 발견을 시간순으로 쌓아둔 findings.md 가 근거 원본이고, 여기서는 그것들을 "왜 했는가 → 무엇을 실험했는가 → 결과 → 개선 방법 → 어떻게 개선했는가 → 결과 → 결론" 순서로 다시 엮는다. 빠뜨린 것 없이, 틀렸던 것까지 포함해서.

11. 왜 했는가

1.1 Deletion vector 가 무엇인가

Iceberg 는 데이터 파일을 불변으로 다룬다. 행 하나를 지우려면 파일 전체를 다시 쓰거나, "이 행은 지워졌다"는 별도의 표시를 남겨야 한다. 후자가 merge-on-read 다.

  • V2 는 이걸 positional delete file 로 했다. (파일 경로, 행 위치) 쌍을 담은 Parquet 파일이고, 삭제할 때마다 새 파일이 하나씩 생긴다. 파일이 수천 개로 불어난다.
  • V3 는 이걸 deletion vector 로 바꿨다. 데이터 파일 하나당 RoaringBitmap 하나를 Puffin 포맷에 담는다. 파일 수가 데이터 파일 수를 넘지 않고, 크기도 훨씬 작다.

저장 측면에서는 명백한 개선이다. 이 프로젝트가 묻는 것은 그다음이다 — 읽을 때는?

1.2 읽기 경로에서 무슨 일이 일어나는가

Spark 가 Iceberg 테이블을 벡터화 모드로 읽으면, Parquet 를 5,000행짜리 ColumnarBatch 단위로 디코딩한다. 삭제가 있으면 그 배치에서 지워진 행을 걷어내야 하는데, 그 일을 하는 것이 ColumnarBatchUtil 이다. 구조를 줄이면 이렇다:

// ColumnarBatchUtil.buildRowIdMapping — 살아남은 행의 인덱스를 모은다
int[] mapping = new int[batchSize];
int live = 0;
for (int rowId = 0; rowId < batchSize; rowId++) {
    long pos = batchStart + rowId;
    if (!deletes.isDeleted(pos)) {      // ← 행마다 한 번씩 묻는다
        mapping[live++] = rowId;
    }
}

핵심은 if 안쪽이 아니라 루프 자체다. 삭제율이 0.5% 든 50% 든 isDeleted(pos) 호출 횟수는 언제나 배치 크기와 같다. 800만 행 테이블이면 삭제가 4만 행뿐이어도 800만 번 묻는다.

그리고 isDeleted(pos) 한 번은 공짜가 아니다. RoaringPositionBitmap.contains(long) 은 long 위치를 (상위 32비트 키, 하위 16비트) 로 쪼개고 → 키 배열을 이진 탐색해 컨테이너를 찾고 → 2단 간접을 거쳐야 비로소 비트를 만진다.

1.3 왜 이게 문제라고 의심했는가

RoaringBitmap 은 구간 단위 API 를 이미 갖고 있다 — forAllInRange, forEachInRange, getBatchIterator, rangeCardinality. 배치의 위치는 [batchStart, batchStart+batchSize) 라는 연속 구간이다. 즉 한 번의 구간 순회로 끝날 일을 5,000번의 개별 조회로 하고 있다.

특히 삭제가 하나도 없는 배치조차 5,000번을 다 묻는다. 구간 API 라면 O(1) 이다.

여기까지가 코드를 읽고 세운 가설이다. 이 프로젝트의 첫 번째 규율은 "가설은 가설이라고 적고, 재기 전에는 주장하지 않는다" 이다.

22. 무엇을, 왜 실험했는가 — 설계와 규율

2.1 축 설계 — (d, C, p) 격자

가설이 맞다면 비용은 RoaringBitmap 이 어떤 컨테이너를 고르느냐에 달려 있다. Roaring 은 64K 짜리 "청크" 마다 컨테이너를 따로 고른다:

컨테이너조건표현조회
array카디널리티 ≤ 4096정렬된 char[]이진 탐색 O(log n)
bitmap카디널리티 > 40968KB 고정 비트셋O(1) 비트 테스트
run연속 구간이 적을 때(시작, 길이) 목록이진 탐색

카디널리티 4096 은 청크 밀도로 4096/65536 = 6.25% 다. 그래서 세 축을 잡았다:

  • d — 삭제 밀도. 6.25% 경계를 가로지르게 촘촘히 스윕한다.
  • C — 클러스터링(평균 run 길이 L). 밀도는 고정하고 삭제가 얼마나 뭉쳐 있는지만 바꾼다.
  • p — 점유 청크 비율. 밀도와 L 을 고정하고 "삭제가 있는 청크가 몇 개냐"만 바꾼다.
왜 3점 설계가 아니라 스윕인가: 원안은 A/B/C 세 지점만 잴 생각이었다. 그랬다면 6.25% 경계를 건드리지 못했을 것이다. 실제로 이 경계가 이 프로젝트에서 제일 중요한 발견이 됐다 (F-001, F-007).

2.2 측정 방법과 그 한계

  • 프로파일러: async-profiler 4.5, ctimer 이벤트 (CPU 시간 기반 샘플링). 스택에 DV 프레임이 있으면 그 샘플을 DV 로 귀속하는 inclusive 집계다.
  • 분모 두 개: DV/전체(JVM 기동·JIT·GC 포함, 보수적) 와 DV/스캔(리더 서브트리 안). 게이트 판정은 보수적인 쪽을 썼다.
  • 왜 CPU 시간인가: I/O 대기가 분모에 안 들어간다. 이게 나중에 F-019 에서 "콜드 캐시로 바꿔도 비중이 안 움직인다"는 결과의 원인이 된다.
  • 환경: Spark 4.0.4 / Iceberg 1.11.0 / JDK 17 / WSL2 Ubuntu 24.04 / AMD Zen 3, local[4], 8M 행 × 20컬럼 × 4파일.

2.3 노이즈를 먼저 쟀다

"차이가 있다"고 말하려면 차이 없음이 얼마나 흔들리는지를 먼저 알아야 한다. 같은 설정을 15개 × 3회 반복해서 노이즈 바닥 = 중앙값 9.7%, 최대 25.9% 를 확정했다 (F-010).

이게 없었다면 아래 여러 결과를 잘못 읽었을 것이다. 실제로 반복 측정이 단일 측정본의 결론 두 개를 뒤집었다 (10장 참조).

나중에 밝혀진 것: 9.7% 는 워크로드가 아니라 내 WSL2 개발 환경의 성질이었다. 전용 EC2 인스턴스에서는 7.0~12.7% 였다 (F-020).

33. 결과 ① 진단 — 문제가 실재하는가

3.1 컨테이너 경계는 실재한다

먼저 파서를 만들어 Puffin 파일에서 컨테이너 타입을 직접 읽었다 (F-004, F-006). 그리고 실제 테이블에서 경계를 확인했다:

전이 폭이 0.30%p 다 (F-007). 청크 밀도 6.10% 에서는 거의 다 array, 6.40% 에서는 거의 다 bitmap 이다. 이항분포로 예측한 전이 곡선과 3.7%p 이내로 일치했다. 즉 이건 우연이 아니라 구조다.

3.2 컨테이너 타입이 비용을 4배 가른다 — 그리고 방향이 직관과 반대다

같은 5,000행 배치에 현행 경로(contains() 행당 1회)를 마이크로벤치로 재봤다 (F-001):

함의가 반직관적이라 중요하다. "삭제를 조금만 하면 싸다" 가 아니다. 삭제율 0~6.25% 구간 전체가 행당 비용이 가장 비싼 영역이고, 실무 CDC 워크로드는 대부분 여기 있다.

정렬이 좋은 이유는 run 컨테이너가 되어서가 아니라, 삭제가 있는 청크를 비우기 때문이다. §8.2 의 "어중간하게 뭉치면 손해"와 같은 이야기다 — run 이 되는 것 자체는 이득이 아니었다.

3.5 게이트 — 이걸 계속할 가치가 있는가

Phase 0 의 판정 기준은 "DV 체크가 스캔 CPU 의 5% 이상"이었다. 결과는 40% (F-005). 게이트 GO.

음성 대조군도 뒀다 — DV 가 없는 테이블에서 DV 샘플이 정확히 0 이었다. 오탐이 없다는 뜻이므로 위 수치를 보정 없이 쓸 수 있다.

그리고 벽시계로도 보인다: 0.5% 만 삭제해도 스캔이 +13% 느려진다.

6.2 그런데 경계가 있다 — 넓은 투영에서는 사라진다

20컬럼을 투영하면 DV 체크 CPU 는 여전히 6.33배 줄지만, 벽시계 차이는 주장할 수 없다 (F-015). DV 비중이 4.8% 로 떨어져 노이즈에 묻히기 때문이다.

그래서 "언제 이 개선이 보이는가"를 따로 쟀다:

  1. 손익분기는 컬럼 수 5~10개 사이 (F-016) — 라고 처음엔 적었다.
  2. 그런데 컬럼 타입을 통제해보니 컬럼 수 가설이 죽었다 (F-017):

정수 10개(21.6%) > 문자열 3개(10.6%). 3/3 밀도에서 방향이 반대였다. md5 문자열 컬럼 1개 = 정수 컬럼 8~10개어치.

  1. 문자열 길이를 통제하니 답은 둘 다였다 (F-025, F-030 정정 후):

비용 = 1,808 + 61.6 × 길이 (R² = 0.95). 컬럼 고정비와 바이트당 비용이 둘 다 실재한다.

  1. 결국 진짜 축은 하나의 숫자였다 (F-018):

wall 절감 = 0.53 × 샘플 절감 이라는 24점 회귀에서, 손익분기는 "DV 체크가 스캔 CPU 의 21% 이상" 이다. 컬럼 수도 타입도 그 비중을 정하는 입력일 뿐이다.

이 0.53 이라는 보정 계수의 정체는 한참 뒤에야 밝혀진다 → 9.5.

6.3 배치 크기를 바꿔도 결론이 흔들리지 않는다

배치 크기를 1,000 ~ 20,000 (20배 범위) 로 스윕해도 최소 5.68배가 유지됐다 (F-014). 다만 여기서 내 기전 모델이 틀렸다는 걸 발견하고 고쳤다 (10장 참조).

즉 일 단위 적재 + 하루 수백 회 조회하는 분석 테이블이면 며칠 만에 회수되고, 스트리밍 upsert 로 자주 다시 쓰는 테이블이면 손해다.

8.3 처방을 한 문장으로

삭제가 적고(청크 밀도 6.25% 아래), 소수 키 값에 몰려 있고, 한 번 쓰고 수백 번 읽는 테이블이면 삭제 키로 정렬하라. 삭제가 많으면 이득이 3분의 1로 줄고, 어중간하게 뭉치면 손해이며, 자주 다시 쓰는 테이블이면 쓰기 비용이 이득을 넘는다.

조건이 네 개나 붙는 처방이지만, 그 조건들이 전부 측정된 것이라는 게 이 프로젝트가 내놓을 수 있는 최선이다. 조건 없이 "정렬하세요"라고 쓰는 편이 읽기는 좋지만 그건 광고다.

9.1 8개월 동안 "PMU 가 없다"고 적어두고 확인을 안 했다

F-001 은 4.1배의 이유를 이렇게 설명했다: "array 는 이진 탐색이라 분기 예측 실패가 많고, bitmap 은 분기가 없고 L1 에 상주한다." 근거는 비용 곡선의 모양뿐이었다.

확증하려면 하드웨어 카운터가 필요한데, README·SETUP·findings 등 8곳에 "WSL2 라 하드웨어 PMU 가 없다 → 확증은 AWS .metal 인스턴스에서" 라고 적어뒀다.

2026-09-07 에 그냥 쳐봤다. 있었다. WSL2 커널이 Hyper-V vPMU 를 노출하고 있었고 branch-misses, cache-misses, cycles 가 전부 값을 준다. 확인 명령은 README 에 이미 적혀 있었는데 .metal 에서 실행하라는 맥락으로만 적혀 있어서 로컬에서 칠 생각을 못 했다 (F-028).

  • Q_P8 채점 → DV 비중(스캔 서브트리 기준)에 perf stat 총량(프로세스 전체 기준)을 곱해 "총 추가 실패의 183.9%" 라는 말이 안 되는 값을 냈고 그 상태로 "맞음" 판정이 났다. 분모를 맞추니 34.9% 이고 판정이 "절반만 맞음"으로 뒤집혔다 (F-032).

10.4 같은 함정을 반복해서 밟은 것

config.env 오버라이드 함정 — 일곱 번. 두 변종이 있다:

  • 변종 A: config 가 VAR=값 으로 하드코딩하면 VAR=x ./script 가 조용히 무시된다. (REPS, WIDE_COLS, DENSITIES_BP, ROWS_PER_FILE)

게이트가 산출물이 아니라 로그를 본 것 — 세 번.

1111. 최종 결론

11.1 이 문제가 당신에게 해당되는가

해당된다면:

  • Iceberg V3 테이블을 merge-on-read 로 쓰고 있고,
  • 좁은 투영(몇 컬럼만 SELECT)이 많고,
  • 삭제율이 청크 밀도 0~6.25% 구간(= 대부분의 CDC 워크로드)이고,
  • 쿼리가 스캔 위주다(무거운 집계가 없다).

판정 기준 하나로 줄이면: DV 체크가 스캔 CPU 의 20% 이상이면 이 패치가 벽시계로 보인다. 그 밑이면 CPU 는 줄어도 쿼리 시간은 안 변한다.

  1. 행 단위 프로브가 좁은 스캔에서 스캔 CPU 의 43~58% 를 차지한다.

11.3 이 프로젝트가 방법론으로 남기는 것

숫자보다 이게 더 오래 갈 것 같다:

  • 예측을 먼저 적어라. 이 프로젝트는 예측이 15번 빗나갔고, 그때마다 배웠다. 적어두지 않았다면 전부 "예상대로였다"가 됐을 것이다.

  • 숫자가 안 움직이면 의심해라. 10배 일했는데 샘플이 줄면 설정이 안 먹은 것이다.

1313. 한계

측정 환경

  • 주 측정은 WSL2 개발 머신이다. 노이즈 중앙값 27.2% 로, 전용 인스턴스(7.0~12.7%)보다 훨씬 시끄럽다. "노이즈 안"이라고 적은 것들은 조용한 기계에서 갈릴 수 있다.
  • 테이블 모양이 하나다: 8M 행 / 4파일 / 20컬럼. 파일 수천 개, 중첩 타입, 술어 있는 스캔은 안 쟀다.
  • 벤치는 JDK 21, Spark 측정은 JDK 17 이다 (서로 다른 축이므로 섞어 읽으면 안 된다).

방법론의 한계

  • ctimer / cycles 는 inclusive 샘플링이다. 스택에 DV 프레임이 있으면 그 샘플 전체를 DV 로 센다. 배타적 자기 시간이 아니다.
  • 프로파일 비중과 벽시계 사이에는 고정비 희석이 있다 (보정 ≈ 0.45~0.53). 그 정체가 JIT 이라는 것까지는 밝혔지만 (F-033), 남은 부분은 미상이다.
  • 클러스터링 축(C)과 p 축은 술어를 조작한 합성 축이다. 실제 정렬은 F-023/F-026 이 따로 쟀다.

🟡 측정했지만 주장하지 못하는 것

  • 반등의 DV 사이클 증가(+15.5%) — 범위가 겹친다. (다만 기전은 닫혔다 — 분기를 지우면 100% 사라진다, F-037)
  • ~~d=6.1% 의 patched 6/6 저하~~ → 노이즈로 확정됐다 (F-038, 6/12 p=1.00).
  • ~~셔플 축의 예측 효과 — 노이즈 바닥 밑~~ → 전용 인스턴스에서 전부 판정됐다 (F-042). 다만 q2 의 크기(−3.7%)는 여전히 주장하지 않는다 — 부호검정은 p=0.00 인데 문턱(9.7%)이 WSL2 값이라, 결과에 맞춰 문턱을 낮추지 않는다.
  • 파일 수 축에서 S3 가 EBS 보다 1.0%p 더 나쁜 것 — 흩어짐 안이다 (F-041).
