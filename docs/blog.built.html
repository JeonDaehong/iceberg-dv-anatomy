Apache Iceberg V3 · Deletion Vector

삭제를 더 많이 할수록 스캔이 싸진다

Roaring 컨테이너가 6.25% 에서 갈리고, 그 경계 바로 아래가 가장 비싸다. 찾고, 고치고, 19번 빗나간 기록.

발견 44개 측정 축 28개 빗나간 예측 19개 Spark 4.0.4 · Iceberg 1.11.0 최종 2026-09-08
한 문장으로: Iceberg V3 의 deletion vector 는 삭제율이 6.25% 를 넘는 순간 내부 자료구조가 바뀌고, 그 경계 바로 아래가 가장 비싸다. 좁은 스캔에서는 그 체크가 CPU 의 절반을 먹는다. 175줄을 고쳐 최악 지점에서 9.28배를 줄였다. 그리고 그 과정에서 내 예측이 19번 빗나갔다. 패치는 apache/iceberg#18027 로 올려뒀다. 이 글은 그 PR 의 결과를 기다리지 않는다 — 아래 숫자들은 머지 여부와 무관하게 참이거나 거짓이다.

이 글은 결과보다 어떻게 틀렸는지에 대한 이야기다. 숫자는 다 아래에 있고, 전체 측정 기록과 서사 문서는 저장소에 있다.

11. 이상한 곡선에서 시작했다

Merge-on-read 테이블에서 행을 지우면 Iceberg 는 데이터 파일을 다시 쓰지 않는다. 대신 "이 파일의 몇 번째 행이 지워졌다"를 Roaring bitmap 으로 적어 옆에 둔다. 읽을 때는 행마다 isDeleted(position) 을 물어보고 살아남은 행만 통과시킨다.

상식적인 기대는 이렇다 — 많이 지울수록 읽기가 느려진다. 지워진 행이 많으면 비트맵이 크고, 체크할 게 많고, 그러니 비싸질 것이다.

8백만 행 테이블에 삭제율만 바꿔가며 프로파일을 찍었다. 곡선이 이렇게 나왔다.

삭제율 dDV 체크 샘플 (범위)
0.50%599 (576–633)
5.00%746 (700–798)오르막
6.10%872 (838–909)← 정점
6.25%654 (617–702)절벽

삭제율에 따른 DV 체크 CPU. 6.1% 에서 정점 872, 7% 에서 최저 394.

삭제율 6.1% 가 7% 보다 2.22배 비싸다. 더 적게 지웠는데 더 비싸다. 그리고 최적점은 6.4~7% 라는 좁은 골짜기다.

22. 잠깐 — Deletion Vector 가 뭔가

곡선 이야기를 더 하기 전에 배경을 깔아야 한다.

Iceberg 같은 테이블 포맷에서 행 하나를 지우는 방법은 두 가지다. 데이터 파일을 통째로 다시 쓰거나(copy-on-write), "이건 지워졌다"는 표시를 옆에 두거나 (merge-on-read). 후자가 쓰기는 싸고 읽기는 비싸다. 이 글은 그 "읽기가 비싸다"의 정체를 파는 이야기다.

V2 에는 표시하는 방법이 두 가지 있었다.

무엇으로 지목하나읽을 때
position delete파일 + 몇 번째 행위치만 비교하면 된다
equality delete컬럼 값 (user_id = 12345)실제 값을 읽어서 비교해야 한다

position delete 는 지운 위치를 행마다 한 줄씩 파일에 적는다. 삭제가 많아지면 그 파일 자체가 커지고, 읽을 때 정렬·병합하는 비용도 같이 커진다.

V3 의 deletion vector 는 그 목록을 비트맵 하나로 바꾼 것이다.

data-file-a.parquet
        │
        └── deletion vector
                 └── 지워진 행 위치들의 비트맵

파일당 DV 는 최대 하나다. 그래서 리더가 파일 하나를 열 때 병합할 삭제 파일이 여러 개 널려 있지 않고, "이 파일에 대한 비트맵 하나" 만 보면 된다.

equality delete 는 V3 에도 그대로 남아 있다. 값을 봐야 판정되는 삭제는 위치로 바꿔칠 수 없기 때문이다. 이 구분은 나중에 패치를 어디까지 적용할지 정할 때 다시 나온다.

그리고 그 비트맵 구현이 Roaring bitmap 이다. 곡선의 정체가 거기 있었다.

33. Roaring bitmap 은 하나의 비트맵이 아니다

이름은 비트맵인데, 값 전체를 하나의 거대한 비트 배열로 들고 있지 않다.

32비트 값 공간을 상위 16비트로 잘라 청크로 나눈다. 청크 하나가 담당하는 범위는 2^16 = 65,536 개다. 그리고 청크마다 자료구조를 따로 고른다.

컨테이너저장 방식조회
array정렬된 16비트 배열이진 탐색 O(log n)
bitmap8KB 고정 비트 배열비트 테스트 O(1)
run연속 구간을 (시작, 길이) 로 압축구간 이진 탐색

고르는 기준이 중요하다. 청크에 든 원소가 4,096개 이하면 array, 넘으면 bitmap 이다. 값 하나에 2바이트씩 쓰는 배열이 8KB 고정 비트맵보다 작아지는 지점이 거기다.

4,096 / 65,536 = 0.0625 = 6.25%

직접 DV 를 파싱해서 확인해도 그대로였다 — 4,096개는 array, 4,097개는 bitmap.

곡선의 절벽이 정확히 여기다

삭제율이 청크 밀도 6.25% 를 넘으면 컨테이너가 array → bitmap 으로 바뀌고, 조회가 이진 탐색에서 비트 테스트가 된다.

경계 바로 아래(d=6.1%)가 최악인 이유도 같다 — 그때 array 의 카디널리티가 최대(3,998)라 이진 탐색이 가장 깊다. 더 지우면 오히려 자료구조가 좋은 쪽으로 넘어간다.

전이 구간의 폭도 쟀다. 이항분포로 예측한 값과 3.7%p 이내로 맞았다 — 청크마다 카디널리티가 조금씩 다르니 경계가 한 점이 아니라 0.30%p 폭으로 번진다.

표에서 6.25% 와 7% 사이(6.4%)를 뺀 건 의도적이다. 재보면 455 가 나오는데, 7%(394)와의 차이가 15.5% 로 노이즈 바닥 바로 위이고 그 점의 흩어짐이 25.9% 로 전체 측정에서 가장 나쁘다. 두 점의 순서는 주장할 수 없어서 곡선에서 뺐다.

44. 그런데 삭제율만으로 정해지지 않았다

여기까지면 이야기가 깔끔하다. "컨테이너 타입이 비용을 정한다."

그래서 삭제율을 고정하고 다른 걸 바꿔봤다. 0.5% 를 그대로 둔 채, 지워진 위치가 얼마나 뭉쳐 있는지만 바꿨다.

3.53배 차이가 났다. 삭제율도, 지운 행 수도 같은데.

처음엔 run 컨테이너 덕이라고 생각했다. 뭉쳐 있으면 연속 구간으로 압축되니까. 그런데 컨테이너 타입을 똑같이 유지한 채 삭제가 존재하는 청크 수만 줄여도 2.22배가 나왔다. run 은 주연이 아니었다.

그러니까 축이 하나가 아니다:

삭제율          ─┐
청크 내부 밀도   ─┤
삭제 위치의 뭉침 ─┼→ DV 체크 비용
컨테이너 타입    ─┘

여기서 멈췄으면 결론은 "DV 비용은 복잡한 함수다" 였을 것이다. 실제로 한동안 그렇게 생각했다. 그게 틀렸다.

55. 진짜 병목은 DV 가 아니라 읽는 쪽이었다

다음 질문은 이거였어야 했다 — Spark 는 이 비트맵을 실제로 어떻게 읽고 있나?

ColumnarBatchUtil 이다. Spark 의 벡터화 리더가 배치 하나를 처리할 때, 살아남은 행의 번호를 새로 매기기 위해 이렇게 돈다:

for (int rowId = 0; rowId < batchSize; rowId++) {
  long pos = rowStartPosInBatch + rowId;
  if (!deletedPositions.isDeleted(pos)) {
    rowIdMapping[live++] = rowId;
  }
}

배치 기본 크기가 5,000행이니 배치마다 5,000번의 독립적인 조회다.

문제는 pos 가 무작위가 아니라는 것이다. 배치가 읽는 위치는 이미 연속 단조 증가다.

실제로 물어보는 것        알고 있는 것
isDeleted(100)
isDeleted(101)
isDeleted(102)     →      [100, 5100) 구간 전체
   ...
isDeleted(5099)

그런데 isDeleted(pos) 한 번은 불리언 배열 조회가 아니다. Roaring 에서는 매번 이 일을 처음부터 다시 한다:

pos
 └→ 상위/하위 키로 분리
     └→ 비트맵 배열 범위 검사
         └→ 컨테이너 배열 이진 탐색
             └→ 컨테이너 안에서 멤버십 검사

배치 전체가 같은 컨테이너 한두 개에 떨어지는데도, 앞의 세 단계를 5,000번 반복한다. 한 번 찾아두면 되는 것을 행마다 다시 찾고 있었던 것이다.

이게 앞 절의 축들을 다시 설명한다. 청크가 여러 개로 흩어지면 컨테이너 배열이 길어져서 이진 탐색이 깊어진다. 뭉쳐 있으면 짧다. 3.53배도, 2.22배도 결국 "행마다 반복하는 그 탐색이 얼마나 깊으냐" 였다. 컨테이너 타입은 마지막 한 단계일 뿐이었다.

66. 얼마나 비싼가 — 그리고 분모를 밝히는 법

여기서 이 프로젝트가 가장 많이 신경 쓴 부분을 하나 말해야 한다.

"DV 체크가 스캔 CPU 의 53% 를 차지한다"는 문장은 그 자체로는 거의 거짓말이다.

투영 폭DV 체크가 스캔 CPU 에서 차지하는 비중
1 컬럼53.2%
3 컬럼24%
5 컬럼16%
20 컬럼3.75%

투영 폭에 따른 DV 체크 비중. 1컬럼 53.2% 에서 20컬럼 3.75% 로.

분모(Parquet 디코딩)가 컬럼 수만큼 커지기 때문이다. 그래서 이 프로젝트는 큰 쪽만 인용하지 않고 항상 범위로 적는다.

그리고 축이 '컬럼 수' 가 아니라는 것도 재서 알았다. 정수 컬럼 10개(21.6%)가 문자열 컬럼 3개(10.6%)보다 비중이 높다. md5 문자열 컬럼 하나가 정수 컬럼 8~10개어치다. 진짜 축은 컬럼 수가 아니라 디코딩 비용이었고, 손익분기는 하나의 숫자로 수렴한다 — DV 가 스캔의 21% 를 넘느냐.

그 21% 는 환경에 잘 안 흔들린다:

바꾼 것결과
CPU (Zen 3 / Sapphire Rapids / Graviton3)49% / 56% / 54% — ±7%p
스토리지 (웜 / 콜드 / EBS / S3)51.2% / 52.0% / 56.2% / 58.0%
병렬도 (local[1] ~ local[16])보정비 1.30 × N^0.141 — 16배에 1.5배
분산 클러스터42% — 여기서만 내려앉는다

43~58% 는 단일 JVM 조건의 값이다. 분산 클러스터에서는 42% 로 떨어진다.

쿼리에 무거운 집계가 붙으면 쿼리 전체 대비로는 빠르게 밀려난다 — 스캔만 하는 쿼리 19.7% → 작은 집계 10.5% → 큰 집계 3.4%. **그런데 스캔 안에서의 비중은 거의 안 움직인다**(59.6 / 58.0 / 55.6%, 폭 4.0%p).

그래서 이런 그림이 된다:

쿼리절감되는 절대 시간전체 대비 단축
스캔만+0.086초−29.3%
집계-소+0.065초−10.8%
집계-대+0.100초−3.7%

절감되는 절대 시간은 쿼리 종류와 무관하게 상수다(세 범위가 전부 겹친다, 부호 12/12). 같은 행에 같은 DV 작업을 하니 당연한 결과인데, 재보기 전까지는 확인도 반박도 못 했다. 달라지는 건 그게 전체에서 차지하는 비율뿐이다.

이 표는 두 번 잰 것이다. 처음엔 내 노트북(WSL2)에서 쟀고, 집계-대 쿼리에서 패치가 0.176초 느리다(6라운드 중 5라운드)는 결과가 나왔다. 판정 불가로 처리해뒀는데, 전용 인스턴스에서 12라운드를 다시 재니 0.100초 빠르다(12/12) 였다. 없는 회귀를 보고 있었던 것이다.

77. 고쳤다

고칠 것은 하나다. 배치가 이미 알고 있는 구간을 그대로 넘긴다.

PositionDeleteIndex 에 구간 순회 메서드를 하나 추가했다:

default void forEachInRange(long posStart, int length, LongConsumer consumer)

default 구현은 지금의 행 단위 루프 그대로다. 그래서 이 인터페이스를 구현한 바깥 코드는 아무것도 안 고쳐도 계속 돈다. 그리고 실제로 쓰이는 구현체만 재정의한다:

PositionDeleteIndex
   ├── BitmapPositionDeleteIndex → 구간을 32비트 비트맵 최대 2개로 좁혀 한 번씩 훑는다
   ├── EmptyPositionDeleteIndex  → 아무것도 안 한다
   └── (그 외)                    → 기본 구현, 즉 기존 동작

ColumnarBatchUtil 은 삭제된 위치만 받아서 그 사이를 순차로 채운다. 컨테이너를 찾는 앞의 세 단계가 배치당 한 번으로 줄고, 5,000번이 아니게 된다.

apache-iceberg-1.11.0 을 클론해 175줄을 고치고 다시 빌드했다. 같은 테이블에 jar 만 바꿔서 쟀다:

설정컨테이너현행패치본개선
0.5%array674798.56배
6.1%array873949.28배
7.0%bitmap4201133.73배
0.5% 정렬run185613.05배

현행과 패치본 비교. 최악 지점 6.1% 에서 873 → 94.

_deleted 투영 경로는 18.9배(빈틈을 채울 필요가 없어 이득이 더 크다), equality delete 테이블은 회귀 없음(게이트가 기존 루프로 정확히 폴백).

비교가 성립하도록 베이스라인도 릴리스 jar 을 쓰지 않았다. 같은 소스 트리를 패치만 stash 한 상태로 다시 빌드했다. 두 jar 의 유일한 차이가 우리 diff 여야 한다.

왜 equality delete 는 그대로 뒀나

패치는 삭제 경로 전체를 바꾸지 않는다. DV·position delete 만 구간 순회로 가고, equality delete 는 기존 루프를 그대로 쓴다.

DV / position delete   →  구간 순회 (새 경로)
equality delete        →  행 단위 평가 (그대로)

이유는 §2 에서 이미 나왔다. position 기반 삭제는 위치만 있으면 판정이 끝나므로 구간을 한 번 훑으면 된다. equality delete 는 행의 값을 읽어서 조건을 맞춰봐야 하므로 구간을 안다고 건너뛸 수 있는 게 아니다.

게이트는 deletes.hasEqDeletes() 하나다. equality delete 가 있는 테이블에서 회귀가 없다는 것도 따로 쟀다 — 코드 경로가 바뀌지 않으니 당연하지만, 당연한 것도 재기 전에는 확인이 아니다.

결과가 같은지 먼저 확인했다

성능보다 이걸 먼저 했다. 두 jar 로 테이블 7개에 대해:

count(*)
sum(id)
min(id) / max(id)

전부 일치했다. Iceberg 자체 테스트도 통과했고, 새 API 에 대해 경계 조건 테스트를 따로 썼다 — 빈 인덱스, 길이 0과 음수, 시작 포함·끝 제외, 오름차순 보장, 65,536 청크 경계, 2^32 키 경계, 할당되지 않은 키, run 컨테이너, 그리고 무작위 구간을 기존 행 단위 방식과 대조하는 것까지.

마지막 항목이 실질적으로 가장 중요하다. 빨라졌다는 것보다 기존 구현과 답이 같다는 쪽을 증명해야 하는 변경이다.

스캔 서브트리로는 얼마나 줄었나

최악 지점(d=6.1%)에서 DV 체크가 스캔 CPU 의 49.4% → 9.6% 로 내려가고, 스캔 서브트리 전체로는 −44.8% 다.

다만 이 숫자는 그대로 옮기면 안 된다. 프로파일러 샘플 비중이지 벽시계가 아니다. 같은 데이터로 샘플 감소분과 실제 시간 감소분의 비를 재보면 1.7~2.4배가 나온다 — 즉 샘플 비중을 그대로 "쿼리가 이만큼 빨라진다" 로 읽으면 2배 안팎 과장하게 된다. 그래서 이 글은 벽시계를 말할 때 항상 따로 잰 값을 쓴다.

업스트림에 냈다 — 그리고 아직 리뷰 중이다

측정만 하고 끝내지 않으려고 패치를 실제로 제출했다.

PositionDeleteIndex 에 forEachInRange 를 하나 추가하는 형태다. default 구현이 현행 루프라서 외부 구현체는 그대로 돈다. 지금 논의되는 건 주로 공개 인터페이스에 메서드를 더하는 것이 맞느냐이고, 그 답에 따라 패치 모양은 바뀔 수 있다.

그래서 분명히 해두고 싶다 — 아래 숫자들은 그 결론에 의존하지 않는다. 구현이 다른 모양으로 바뀌어도 6.25% 경계는 그대로 있고, 행마다 조회하는 구조가 비싼 것도 그대로다. 내가 주장하는 건 "내 패치가 채택되었다"가 아니라 "이 비용이 여기 있고, 이렇게 재면 보인다"다.

88. 그런데 대부분의 쿼리에서는 안 보인다

여기가 이 프로젝트에서 가장 쓰기 싫었던 절이다.

20컬럼 넓은 투영에서도 DV 체크 CPU 는 6.33배 줄어든다. 그런데 그 CPU 가 전체 스캔의 4.8% 뿐이라 전체 쿼리 시간으로는 측정되지 않는다.

"그래서 실무에서 몇 % 빨라지나" 의 정직한 답은 "당신이 몇 컬럼을 읽느냐에 달렸고, 20컬럼이면 측정 불가" 다.

절감되는 CPU-초는 실재한다 — 클라우드 청구서는 CPU-초로 온다. 그러나 대시보드의 쿼리 시간은 안 움직인다. 둘 다 사실이고, 둘 다 말해야 한다.

그리고 조건이 하나 더 있다 — 파일이 잘게 쪼개져 있으면 이득이 절반

같은 데이터(3,200만 행)를 파일 4개와 파일 488개로 나눠 담고 재봤다. 파일 경계를 청크(65,536) 배수로 맞춰서 두 테이블의 Roaring 컨테이너가 바이트까지 동일하게 만들었다 — 488개, array:460 + bitmap:28, 3,901,922 B. 삭제된 행도 같다. 남은 차이는 그게 puffin 파일 4개에 담겼느냐 488개에 담겼느냐뿐이다.

배치 루프는 안 움직인다 — 하는 일이 같으니 당연하다. 움직이는 건 파일당 고정비(Parquet 푸터 파싱, DV 하나 더 읽기)다.

그래서 DV 비중이 56.2% → 45.5% 로 떨어지고, 패치 이득도 6.97배 → 3.43배로 준다. 패치가 나빠진 게 아니라, 패치가 못 건드리는 고정비가 분모를 지배하게 된 것이다.

이건 내가 "파일이 많으면 요청 지연이 지배하는데 그건 대기라 비중은 안 변한다" 고 추측으로 적어뒀던 자리다. 틀렸고, S3 를 켜기도 전에 로컬 디스크에서 틀렸다.

S3 에서도 다시 쟀다. 스토리지는 여전히 아무것도 안 바꾼다 — 같은 파일 수에서 EBS 60.7% vs S3 61.1% 이고, 파일이 488개일 때도 49.7% vs 49.0% 다. 움직이는 건 파일 수뿐이고 그 크기도 두 스토리지에서 같다(−11.1%p / −12.1%p).

99. 기전은 세 번 다 내 예상과 달랐다

처음에 나는 이렇게 적었다: "array 컨테이너는 이진 탐색이라 분기 예측 실패가 많아 비싸다."

근거는 비용 곡선의 모양뿐이었다. 8개월 동안 "WSL2 에는 하드웨어 PMU 가 없다" 고 여덟 군데에 적어두고 확인을 안 했다. 어느 날 확인해보니 있었다.

재보니 분기는 비용 차이의 1.4% 만 설명했다. 실제 쿼리 경로에서는 0.2% 였다. IPC 가 4.7 로 상수라 파이프라인은 아예 막히지 않았다. F-001 의 기전 설명은 반증됐다.

그러면 왜 비싼가 — 명령어 수다. 그냥 일을 더 한다. 그리고 그건 컨테이너 타입 이야기가 아니라 "행마다 호출한다"는 구조 자체의 이야기다 (가장 싼 bitmap 도 행당 86.5 명령어를 쓴다). 기전이 패치를 가리켰다.

예외가 딱 하나 있었다. 삭제율이 아주 높을 때(d=8%→50%)의 반등이다. 여기서는 if (!contains(pos)) 가 정확히 동전 던지기가 된다. 분기 실패가 40% 늘었다. 그런데 처음 계산으로는 늘어난 사이클의 28.5% 만 설명됐고, 나머지 55% 는 이름이 없었다.

루프 몸통을 변형 6종으로 잘라 다시 쟀다:

변형남긴 것d=8%d=50%증가폭
현행분기 O · 저장 O28.8837.30+29.1%
분기 제거분기 X · 저장 O28.0227.90−0.4%
조회만분기 X · 저장 X27.0621.78−19.5%

분기를 지우면 반등이 100% 사라진다. 그런데 branch-misses 카운터가 세는 건 그중 33% 뿐이다. 나머지는 어디 있나 —

d=8%d=50%
명령어/op587,777604,491 (+2.8%)
IPC4.623.68 (−20.3%)

일이 늘어서가 아니라 파이프라인이 막혀서다. 예측 불가능한 분기는 투기 실행을 끊어 루프를 직렬화하고, 그 정지 시간은 오예측 카운터가 아니라 IPC 로만 보인다. 미상 55% 는 새 범인이 아니라, 카운터가 3분의 1만 세고 있던 같은 비용이었다.

이 실험에서 변형 6개 중 둘은 설계 실수였다. 저장을 없앤 변형은 JIT 이 조건문을 산술로 바꿔버려(분기 실패 1,084 → 4.1) 대조군이 못 됐다. 하드웨어 카운터를 같이 안 찍었으면 "저장이 범인" 이라는 정반대 결론을 냈을 것이다.

1010. 오늘 할 수 있는 것 — 정렬. 조건 네 개.

패치가 업스트림에 들어가기를 기다리는 동안 할 수 있는 게 있다. 삭제 키로 정렬해서 테이블을 쓰면 삭제가 소수 청크에 몰리고 DV 체크가 2.80배 싸진다. 패치가 와도 둘은 서로 대체하지 않는다 — 둘 다 하면 12.39배다.

그런데 조건이 네 개 붙는다. 전부 측정된 것이다.

조건안 지키면
1삭제가 소수 키 값에 몰릴 때만고유값 ~1천 2.78배 / ~10억 0.89배 (손해)
2삭제율이 경계 아래일 때 크다경계 위에서는 1.26배로 줄어든다

조건 3 을 재면서 놀란 게 하나 있다. 정렬하면 파일이 작아질 줄 알았는데 2.6% 커졌다. 컬럼별로 쪼개보니 이유가 정확했다 — 정렬 키는 399배 작아지는데, 원래 파일 안에서 완벽한 등차수열이던 id 가 2배가 된다. 델타 인코딩이 먹던 이득이 날아가는 것이다.

삭제 키로 정렬하면 원래 정렬돼 있던 컬럼(자동증가 id, 적재 타임스탬프)이 커진다. 아무도 말해주지 않는 청구서다.

그리고 정렬이 좋은 이유가 내 생각과 달랐다

"정렬하면 run 컨테이너가 되어서 싸진다" 고 1년 가까이 적어왔다. 그런데 이 설명에는 구멍이 있었다 — 정렬하면 컨테이너 타입(array→run)과 개수(124→12)가 같이 움직인다.

타입은 그대로 두고 개수만 줄이는 축을 따로 만들어 쟀다.

타입을 하나도 안 바꾸고 개수만 줄였는데 2.22배가 나왔다. 정렬이 좋은 이유는 run 컨테이너가 되어서가 아니라 삭제가 있는 청크를 비우기 때문이다. 조건 4("어중간하게 뭉치면 손해")와 같은 이야기다 — run 이 되는 것 자체는 이득이 아니었다.

1111. 이 프로젝트가 진짜 남기는 것

숫자보다 이게 더 오래 갈 것 같다.

예측을 먼저 적어라

모든 실험 스크립트의 헤더에 측정 전에 예측을 적었고, 채점 도구는 그 예측을 다시 적지 않는다(적으면 사후에 조용히 고칠 수 있게 된다).

그 결과 예측이 19번 빗나갔다. 적어두지 않았다면 전부 "예상대로였다" 가 됐을 것이다. 빗나간 것들 중 몇 개:

  • "분기 예측이 컨테이너 비용을 설명한다" → 반증
  • "손익분기는 컬럼 수다" → 죽었다. 축은 디코딩 비용이었다
  • "정렬하면 파일이 작아진다" → 반대로 커졌다
  • "본전 회수 10회 미만" → 약 300회. 30배 빗나갔다
  • "컨테이너 개수만 줄이면 1.5배 미만" → 2.22배

빗나가는 방식도 두 가지였다. 예측이 틀린 경우와, 예측을 시험하지도 못한 경우다. 후자가 더 무섭다 — 저장을 없앤 변형은 JIT 이 조건문을 산술로 바꿔버려서 대조군이 못 됐고, 카운터를 안 찍었으면 그걸 모른 채 "저장이 범인" 이라고 발표했을 것이다. 또 한 번은 같은 문서의 T2 와 T3 이 서로 모순됐는데(한쪽은 "패치 일량은 삭제 수에 비례" 라고 쓰고 다른 쪽은 그걸 무시했다) 측정이 그걸 잡아냈다.

노이즈를 먼저 재라 — 이게 가장 비싼 교훈이었다

처음엔 노이즈를 Poisson 근사 ±√n 으로 추정하고 "350 ± 19 이므로 명확히 분리됨" 이라고 적었다. 같은 설정을 실수로 두 번 재보니 실제 흩어짐은 20~41% 였다. 두 배가 아니라 자릿수가 틀렸다.

그래서 모든 설정을 3회 반복으로 다시 쟀고, 흩어짐 중앙값 9.7% 를 확정한 뒤 "이 값보다 작은 차이는 주장하지 않는다"를 채점 코드에 박아넣었다. 사람이 표를 보고 판단하면 반드시 노이즈를 신호로 읽는다.

큰 주장 셋은 살아남았고 오히려 커졌다. 죽은 건 미세 구조뿐이었다. 다만 이건 사후적으로 운이 좋았던 것이지, 반복 없이 주장했던 방법이 옳았던 건 아니다.

전제도 측정 대상이다

"WSL2 에는 PMU 가 없다" 를 여덟 군데에 적고 8개월을 버렸다. 확인해보니 있었다. .metal 인스턴스를 빌리려던 계획이 통째로 필요 없었다.

"환경 때문에 못 한다" 는 문장을 쓸 때마다, 그게 측정된 것인지 물어야 한다.

게이트는 산출물을 봐라

"✅ 완료 (0초)" 는 거짓말을 한다. 스크립트가 아무것도 안 하고 성공으로 끝날 수 있다. 그래서 모든 게이트가 로그가 아니라 산출물(파일 수, 행 수, 컨테이너 수)을 센다.

그리고 격자를 만들 때는 실제로 서로 다른 데이터가 나오는지 먼저 검증한다. 한 축은 이걸 안 해서 통째로 날아갔다 — 파일당 청크가 30개뿐이라 파라미터를 바꿔도 같은 테이블이 나왔고, 서로 다른 두 설정을 만들고 있다고 믿으면서 같은 걸 두 번 쟀다.

100% 를 넘는 비율이 나오면 멈춰라

한 번은 "총 추가 실패의 183.9%" 라는 값을 내고 그 상태로 "맞음" 판정이 났다. 분모가 섞여 있었다(스캔 서브트리 기준 비중에 프로세스 전체 기준 총량을 곱했다). 맞추니 34.9% 였고 판정이 "절반만 맞음" 으로 뒤집혔다.

정직하게 적는다.

  • 파일 수천 개짜리 테이블. 488개까지 EBS·S3 양쪽에서 쟀다. 수천 개는 안 쟀다.
  • 크로스 리전 S3. 같은 리전에서만 쟀다. 대기가 훨씬 크겠지만 그건 CPU 시간이 아니므로 비중을 못 바꾼다는 게 이 축의 결론이다 — 다만 안 쟀다.
  • 더 큰 클러스터. 익스큐터 2개짜리에서 42% 였고, 이건 하한이다.
  • 조인이 붙은 쿼리. 집계 두 종만 쟀다.
  • mapping[live++] 의 저장 주소 의존. 살지도 죽지도 않았다 — 변형 하나가 두 가지를 같이 바꿔서 갈리지 않는다.
  • 샘플 → 벽시계 보정 0.53 의 나머지. 정체가 JIT 이라는 것까지는 밝혔다 (프로세스 CPU 의 41.6%). 즉 우리 벽시계 숫자는 실무에 대해 보수적이다 — 오래 사는 익스큐터에서는 희석이 약하다.

부록 — 측정 조건

모든 수치는 설정당 3회 이상 반복의 중앙값이다. 반복 흩어짐은 중앙값 9.7%.

  • Ryzen 5 5600X (Zen 3) · WSL2 · Spark 4.0 local[4] · JDK 17
  • 로컬 NVMe 웜 캐시 (825MB 테이블, 측정 중 I/O ≈ 0)
  • 배치 크기 Iceberg 기본 5,000 · 1컬럼 좁은 투영 (달리 적지 않은 한)
  • 클라우드 축은 m7i.xlarge (Sapphire Rapids) / m7g.xlarge (Graviton3) 전용 인스턴스
  • 벤치는 JDK 21, Spark 측정은 JDK 17 — 서로 다른 축이므로 섞어 읽으면 안 된다

노이즈 바닥 9.7% 는 측정 대상의 성질이 아니라 WSL2 의 성질이었다. 같은 테이블·같은 jar·같은 스크립트로 기계만 바꿔 재면 흩어짐이 49.4% → 15.0% 다.

그리고 그게 실제로 한 축의 부호를 바꿨다 — 집계-대 쿼리에서 노트북은 "패치가 느리다"(1/6)를, 전용 인스턴스는 "빠르다"(12/12)를 냈다. 로컬에서 "노이즈 안" 이라고 적은 것들은 조용한 기계에서 갈릴 수 있다.

한 가지 덧붙이면, "조용하다"는 지표마다 다르다. 파일 수 축에서는 프로파일 샘플의 흩어짐이 3.3배 줄었는데, 셔플 축에서는 샘플 흩어짐이 거의 그대로였고(22.0 → 20.7%) 대신 wall-clock 쌍차가 조용해졌다. 무엇으로 판정하느냐에 따라 필요한 환경이 다르다.
