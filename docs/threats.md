# 위협 요인 (Threats to Validity)

> 이 문서는 **우리 결과를 공격하는 방법**을 우리가 먼저 적어둔 것이다.
> 각 항목은 "지금 데이터로 막을 수 있나"를 명시한다. 못 막는 건 못 막는다고 적는다.
> 상태: ✅ 방어됨 · ⚠️ 논리는 있으나 데이터 없음 · ❌ 못 막음 · 🔄 측정 중
>
> 측정 조건 자체는 [findings.md 의 「측정 조건」](findings.md) 참조.

## A. "클러스터를 늘리면 되는 것 아니냐" ⚠️

**반론의 형태**: 스캔이 느리면 노드를 더 붙이면 된다. CPU 몇 %는 돈으로 해결된다.

**우리 답**: 이건 **행당** CPU 비용이다. 노드를 늘리면 wall-clock 은 줄지만
**CPU-초(= 청구 금액)는 그대로**다. 데이터가 2배면 DV 체크도 2배다.
스케일아웃은 이 비용을 없애지 못하고 나눠 가질 뿐이다.
패치는 **일 자체를 줄인다** — 행당 이진 탐색을 제거한다.

**그런데 이 반박은 아직 완성되지 않았다.** 성립하려면 "CPU 가 실제로 병목"임을 보여야 하는데,
우리는 **웜 캐시 · 로컬 NVMe 에서만** 쟀다. 심사자가
*"S3 에서는 I/O 바운드라 CPU 가 놀고 있고, 그러면 이 비용은 공짜다"* 라고 하면
**반박할 데이터가 없다.**

→ **필요한 실험**: S3/MinIO 콜드 리드 조건. 이게 A 와 B-2 를 동시에 막는 유일한 실험이다.

## B. "효과가 나오도록 환경을 짜맞춘 것 아니냐"

### B-1. "6.1% 를 골라놓고 최악이라 한 것 아니냐" ✅ 방어됨

- 삭제율을 **0.5%~50%, 14개 지점**으로 스윕하고 곡선 전체를 보고했다.
  최악 지점은 **고른 게 아니라 찾은** 것이다.
- 더 중요한 건 그 위치를 **이항분포로 사전에 예측한 뒤 측정**했다는 점이다
  (F-007, 예측과 3.7%p 이내 일치). 사후 체리피킹의 정반대다.
- 명백한 해법("삭제 키로 정렬해라")을 **직접 시도해 대부분 안 통한다는 것을 보였다**
  (F-009: L=1~8 이득 0). 자기 가설에 불리한 결과를 실었다.
- 대조군(삭제 0)에서 DV 샘플이 **정확히 0** 이라 분류기 오탐이 없다 (F-005).

**주의**: 이전 초안에 "6.1% 는 실무 CDC 가 주로 머무는 구간" 이라는 문장이 있었다.
**근거가 없어 전부 제거했다.** 어떤 삭제율이 "대표값"인지는 측정한 바 없고,
그래서 특정 값을 대표라 부르는 대신 전 구간을 스윕한다.

### B-2. "1컬럼 투영은 짜맞춘 것 아니냐" ❌ → 🔄

**이건 맞는 지적이었다.** README 와 대시보드가 **53.2% 를 헤드라인**으로 썼는데,
우리는 **20컬럼에서 3.75%** 라는 것을 F-005 에서 이미 알고 있었다.
알면서 큰 쪽만 앞세운 것이고, 심사자가 찾아내면 나머지 수치의 신뢰도까지 무너진다.

**대응**: 헤드라인을 숨기는 게 아니라 **범위로** 바꾼다 —
"투영 폭에 따라 스캔 CPU 의 **3.75%~53.2%**". 이게 오히려 더 강한 결과다
(원안 W6 게이트가 예고한 *"환경 함수라는 더 좋은 결과물"*).

**남은 공백**: F-011 의 9.28배는 **전부 1컬럼**이다.
20컬럼에서 패치가 실제로 얼마를 줄이는지는 **측정 중** (F-015 예정).

### B-3. "합성 삭제 패턴 아니냐" ⚠️

균등 랜덤과 블록 클러스터링이라는 **두 극단**을 쟀고 그 사이를 `L` 로 스윕했다.
그러나 **실제 워크로드에서 뜬 테이블은 하나도 없다.**
논문이면 공개 데이터셋 기반 케이스가 최소 하나 필요하다.

## C. "그냥 이렇게 안 하면 되는 것 아니냐" — 대안 봉쇄

| 심사자가 댈 대안 | 상태 | 근거 |
|---|---|---|
| 삭제 키로 정렬해서 써라 | ✅ | 재봤고 문턱이 높다. L=1~8 은 이득 0, nRuns 가 한 자릿수(L≥64)여야 효과 (F-009) |
| 배치 크기를 키워라 | ✅ | 1,000~20,000(20배)에서 개선이 **최소 5.68배 유지**. 설정으로 못 피한다 (F-014) |
| compaction 을 자주 해라 | ⚠️ | 비용 곡선은 있으나(F-008) **compaction 비용을 안 쟀다.** "언제가 이득인가"는 양쪽이 필요 |
| MoR 말고 CoW 를 써라 | ❌ | **미측정.** MoR 의 존재 이유가 쓰기 증폭 회피인데 그 트레이드오프를 곡선 위에 안 올렸다 |

## D. "N=1 머신, 단일 JVM, WSL2 아니냐" ❌ 못 막음

- CPU 한 종류(AMD Zen 3), 머신 한 대, Spark `local[4]`. (~~WSL2라 PMU 없음~~ → vPMU 있음, F-028)
- 특히 **F-008 의 bitmap 구간 반등(1.26배)** 은 분기 예측 가설인데,
  예측기는 마이크로아키텍처마다 가장 크게 다른 부분이라 이식성이 가장 낮다.
- 노이즈 바닥 9.7% 는 Iceberg 가 아니라 **이 박스의 성질**이다.

→ **필요한 실험**: 다른 벤더 CPU 1대 + 베어메탈 `-prof perfnorm`.

**부분적 완화**: 결정론적 결과(경계 4096, 컨테이너 분포, DV 바이트, 패치의 정확성)는
머신과 무관하다. 흔들리는 건 **배율**이지 **방향**이 아니다 —
패치는 엄격히 더 적은 일을 하므로 느려질 수 없다.

## E. "Spark 만의 문제 아니냐" ⚠️

기전은 **Puffin DV + RoaringBitmap 컨테이너 타입**이지 Spark 의 성질이 아니다.
Trino·DuckDB·PyIceberg 모두 같은 구조를 읽으므로 논리적으로는 엔진 무관이다.
**그러나 우리는 Spark 에서만 쟀다.** 최소 한 점이라도 다른 엔진에서 확인해야
"엔진 무관" 을 주장할 수 있다.

## F. "넓은 스캔에서도 패치가 의미 있느냐" 🔄 측정 중

20컬럼에서 DV 비중이 3.75% 라면, 그 안에서 9배를 줄여도 전체로는 3% 대다.
**그 경우 "그래서 뭐?" 라는 반응이 나오고 실용성 주장이 빈다.**

**현재 상태**: 3라운드 중 1라운드만 측정하고 중단했다. 아직 결론을 내지 않는다.
라운드 1의 wall-clock 은 세 설정 모두 patched 가 오히려 느렸으나
(d610 3.187→3.203s, d50 3.101→3.542s, d700 3.078→3.573s)
실행별 min–max 가 크게 겹치는 1회 측정이라 **아무것도 주장하지 않는다.**
F-010 의 교훈이 정확히 이 상황에 대한 것이다.
재개: `phase2/scripts/06-widescan.sh` (완료된 프로파일은 건너뛴다)

## 논문의 핵심 주장은 무엇이어야 하나

**"DV 체크가 스캔 CPU 의 53%"** 를 헤드라인으로 걸면 안 된다.
조건 의존적이고, 체리피킹으로 읽히고, S3 에서 무너질 수 있다.

**대신 이것을 건다:**

> **Iceberg Deletion Vector 의 스캔 비용은 삭제율에 대해 단조가 아니며,
> 최악 지점이 컨테이너 전이 직전에 결정론적으로 존재한다.**

심사자가 환경으로 깰 수 없는 주장이기 때문이다:

- **결정론적** — 경계 카디널리티 4096 은 컴파일 타임 상수, 컨테이너 분포는 이항분포
- **사전 예측 후 검증** — 반증 가능한 설계였음을 보일 수 있다
- **엔진 무관** — 포맷 + 라이브러리의 상호작용이다
- **반직관적** — 더 많이 지울수록 행당 체크가 싸진다
- **처방이 붙는다** — 레이아웃은 문턱이 높고(측정), 리더 수정은 9배(구현·측정·정확성 검증)

53% 는 헤드라인이 아니라
**"이 비용이 실제 쿼리에서 관측 가능한 크기임을 보이는 보조 증거"** 위치다.
