### 어느 수치가 어디까지 따라가나

**🟢 환경 무관 — 어느 머신에서든 동일**

전이 경계 카디널리티 4096(F-004, `ArrayContainer.DEFAULT_MAX_SIZE`는 컴파일 타임 상수) ·
컨테이너 혼합비와 전이 폭 0.30%p(F-007, 이항분포 + 시드 고정 해시라 결정론적) ·
DV 바이트 수와 nRuns(F-009, 파일에서 읽은 값) · **패치의 정확성**(F-011, 테스트와 `sum(id)` 대조).
단 이것들은 *하드웨어* 무관이지 *버전* 무관은 아니다 — RoaringBitmap이 4096을 바꾸면 경계가 움직인다.

**🟡 방향은 유지, 배율은 이동**

컨테이너별 비용 차이(F-001/F-008)와 패치 배속(F-011/F-012). 기전이 구조적이라
**뒤집히지 않는다** — 패치는 엄격히 더 적은 일을 하므로 느려질 수 없고,
array의 `O(log n)` 이진 탐색은 bitmap의 O(1) 비트 테스트보다 쌀 수 없다.
오히려 분기 예측기가 Zen 3보다 약한 코어에서는 **효과가 더 커질 것으로 예상한다**(미측정).

**🔴 환경 민감 — 다른 데서 크게 달라진다**

- **"DV 체크가 스캔 CPU의 43~53%"** — 이 문서에서 가장 취약한 숫자다.
  분모가 *페이지 캐시가 따뜻한* Parquet 디코딩이고 측정 중 I/O가 0이다.
  얼마나 흔들리는지는 이미 우리 데이터 안에 있다: **투영을 20컬럼으로 넓히면 44.2% → 3.75%** (F-005).
  S3 콜드 리드에서는 한 자릿수로 떨어질 것으로 본다(미측정 — 원안 W5–6의 미이행 항목).
  **정직한 표현은 "좁은 투영 · 웜 캐시 · 로컬 디스크에서의 상한"이다.**
- **wall-clock** (+13% / −30.8%) — 같은 이유. 스캔이 0.15~0.22초로 짧아 상대 노이즈도 크다.
- **bitmap 구간 반등 1.26배**(F-008) — 분기 예측 가설. 예측기는 마이크로아키텍처마다
  가장 크게 다른 부분이라 이식성이 가장 낮다.
- **노이즈 바닥 9.7%**(F-010) — Iceberg의 성질이 아니라 **이 WSL2 박스의 성질**이다.
  베어메탈이면 낮고, 시끄러운 공용 VM이면 높다.

이 결과를 공격하는 방법과 각 공격의 방어 상태는 [threats.md](threats.md)에 따로 적어 뒀다.

**미측정 축** (바꾸면 결과가 움직일 것으로 보는 것): 배치 크기 · JDK 버전(JIT) ·
RoaringBitmap 버전 · 오브젝트 스토리지 · CPU 벤더.
파일 수가 많은 큰 테이블은 최상위 이진 탐색 대상이 늘어 **현행 코드가 더 나빠지므로**
우리 주장에 유리한 방향이다.

## F-001 · 컨테이너 타입이 행당 삭제 체크 비용을 4배 가른다 (2026-08-17)

**README 가설 2 확인. 그리고 방향이 직관과 반대다.**

동일한 5000행 배치에 대해 현행 Iceberg 경로(`RoaringPositionBitmap.contains()` 행당 1회)를 측정:

| 청크 밀도 | 카디널리티 | 컨테이너 | 배치당 비용 | 행당 |
|---|---|---|---|---|
| 0.5% | 327 | **array** | 64.99 ± 2.7 µs | 13.0 ns |
| 5% | 3,276 | **array** | **80.22 ± 3.2 µs** | 16.0 ns |
| 12% | 7,864 | **bitmap** | **19.76 ± 2.1 µs** | 4.0 ns |
| 연속 30% | 19,661 | run | 23.15 ± 1.3 µs | 4.6 ns |
| (배치 밖 삭제) | 30,268 | bitmap | 23.45 ± 0.5 µs | 4.7 ns |

**핵심: 삭제를 더 많이 할수록 체크가 싸진다.** array→bitmap 경계(카디널리티 4096 = 청크 밀도 6.25%)를 넘는 순간 행당 비용이 **16.0ns → 4.0ns 로 4.1배 떨어진다.**

기전:
- **array 컨테이너** — 정렬된 `char[]` 이진 탐색. 분기 예측 실패가 많고, 비용이 `log₂(카디널리티)`로 증가한다. 실제로 327→3,276 (log₂ 8.4→11.7, 1.39배) 일 때 비용이 65→80µs (1.23배)로 같은 방향으로 움직였다.
- **bitmap 컨테이너** — 8KB 고정 비트셋의 O(1) 비트 테스트. 분기 없음, L1 상주.

**함의 (반직관적이라 중요)**: "삭제를 조금만 하면 싸다"가 아니다. 삭제율이 **6.25% 부근에서 스캔 비용이 불연속적으로 점프**하고, 그 **아래 구간 전체**(청크 밀도 0~6.25%)가 오히려 **행당 비용이 가장 비싼 영역**이다.
(실무 워크로드가 실제로 이 구간에 얼마나 분포하는지는 **측정한 바 없다.** 그래서 이 문서는 특정 삭제율을 "대표값"이라 부르지 않고 전 구간을 스윕한다.)

이건 Phase 1의 (d, C, p) 격자 설계가 옳았음을 뒷받침한다. 원안의 A/B/C 3점 설계였다면 이 경계를 못 건드렸을 것이다 ([README §4.1](../README.md)).

### 왜 이렇게 큰가

현행은 5000번의 **독립적이고 분기 많은 이진 탐색**을 한다. 배치 안 position이 연속 단조 증가라는 사실이 전혀 활용되지 않는다.
`forAllInRange`는 구간을 한 번 훑으면서 `RelativeRangeConsumer`로 통보하고, **`acceptAllAbsent(from,to)` / `acceptAllPresent(from,to)` 벌크 콜백**이 있어 run 컨테이너나 삭제 없는 구간을 O(1)로 처리한다. 남는 일은 순차 배열 채우기뿐이라 벡터화가 잘 된다.

### 권장: C (`forAllInRange`)

D가 SPARSE에서 근소하게 빠르지만, C를 권한다.
- 모든 패턴에서 최상 또는 근접 (D는 RUN에서 8.3x, C는 3992x)
- 중간 버퍼(`delBuf`)가 불필요 — 콜백이 곧바로 `rowIdMapping`을 채운다
- 의미가 명확: "이 구간의 present/absent를 알려줘"가 정확히 리더가 원하는 것

F(fast-path)는 C에 흡수시켜도 된다. 별도 이득이 없다(C가 이미 빈 구간을 벌크로 처리).

### ⚠️ 이 수치를 어디까지 믿을 수 있나

- **`*` RUN 3992x는 과장이다.** 그 조건은 배치 5000행이 **전부** 삭제된 상태(`live=0`)라 C가 사실상 아무 일도 안 한다. 부분 겹침 케이스를 추가 측정해야 한다. → TODO
- **마이크로벤치다.** 여기서의 132x가 쿼리 132x가 아니다. 실제 절감 상한은 Phase 0 게이트가 잴 "DV 체크가 스캔 CPU에서 차지하는 비중"이다(암달의 법칙).
- **개발 머신(Windows, JDK 21)** 측정. 사이클/분기실패 귀속은 Phase 2의 `.metal`에서 `-prof perfnorm/perfasm`으로 확정한다.
- **버퍼를 재사용**해 알고리즘만 비교했다. 실제 Iceberg는 배치마다 `new int[batchSize]`를 할당하므로 할당/GC 비용은 미반영.
- 벤치는 `rpb.contains()`를 **직접** 호출한다. 실제 Iceberg는 `PositionDeleteIndex` 인터페이스를 거치므로(호출 지점이 megamorphic일 수 있음) **현실의 baseline은 이보다 느릴 가능성이 높다.** 즉 이 배속은 보수적이다.

### 정합성

6개 구현 전부가 baseline과 **바이트 단위로 동일한 `rowIdMapping`과 live count**를 낸다. `@Setup`에서 assert로 검증하며, 하나라도 어긋나면 벤치가 시작되지 않는다.

## F-004 · dv-inspect 파서 검증 완료, 4096 경계 실측 확인 (2026-08-17)

Roaring portable 포맷을 직접 파싱하는 `tools/dv_inspect.py`가 Java 정답지와 **9/9 일치**.
리플렉션 의존 없음 → [README 리스크 R5](../README.md) 해소.

```
boundary_6     1개 [a]   ok   PASS     카디널리티 4096 -> array
boundary_6b    1개 [b]   ok   PASS     카디널리티 4097 -> bitmap
multi_chunk    3개 [abr] ok   PASS
```

**array/bitmap 전환점이 정확히 4096 (청크 밀도 6.25%)** 임을 실측 확인. F-001의 비용 점프 지점과 정확히 일치한다.

### 실제 포맷 (문서와 달랐던 점)

`BitmapPositionDeleteIndex.serialize()`의 실제 바이트 레이아웃:

```
length  4 bytes  BIG-endian    <- magic + bitmap 길이 (자기 자신·CRC 제외)
magic   4 bytes  d1 d3 39 64
bitmap  length-4 bytes         <- 64비트 확장 portable Roaring
crc     4 bytes  BIG-endian    <- magic + bitmap 에 대한 CRC-32
```

처음에 (a) 길이 프리픽스의 존재와 (b) Roaring cookie 상수를 잘못 가정했다.
실제 값은 `SERIAL_COOKIE_NO_RUNCONTAINER = 12346 (0x303A)`, `SERIAL_COOKIE = 12347 (0x303B)`.

### 부수 관찰: run 컨테이너의 압축률

| 픽스처 | 삭제 행 | 컨테이너 | 바이트 |
|---|---|---|---|
| `run_contig` | 19,661 | run (1개 run) | **6 B** |
| `dense_12` | 7,864 | bitmap | 8,192 B |
| `run_frag` | 24,000 | run (200개 run) | 800 B |

연속 삭제 19,661행이 **6바이트**. 이건 README §3-A(정렬 레이아웃 처방)의 저장 측 근거가 된다 — 단, F-001에서 보듯 **run이 항상 스캔에 유리한 건 아니다**(run 23.15µs vs bitmap 19.76µs). "공간 최적 ≠ 스캔 최적"([README §4.2](../README.md))을 파고들 지점.

**재현**: `python tools/verify_parser.py`

## F-005 · Phase 0 게이트 = **GO**. DV 체크가 스캔 CPU의 40%를 먹는다 (2026-08-17)

**프로젝트 최대 리스크(암달의 법칙, [README §4.5](../README.md)) 해소.**

WSL2 / Ubuntu 24.04 / Spark 4.0.4 / Iceberg 1.11.0 / JDK 17, 800만 행 × 4파일(파일당 30.5 청크), async-profiler `ctimer`.

| 프로파일 | DV/전체 CPU | **DV/스캔 서브트리** |
|---|---|---|
| `none` (대조군) 1컬럼 | 0.00% | 0.00% |
| `none` 20컬럼 | 0.00% | 0.00% |
| **`sparse` (0.5% 랜덤) 1컬럼** | **8.00%** | **40.37%** |
| `sparse` 20컬럼 | 1.87% | 3.75% |
| `run` (연속 30%) 1컬럼 | 3.32% | 21.94% |
| `run` 20컬럼 | 0.66% | 1.30% |

**희소 삭제 + 좁은 스캔에서 DV 체크가 스캔 CPU의 40%를 차지한다.** 게이트 기준 5%를 크게 넘긴다.

### 대조군이 분류기를 검증했다

`none`(DV 없음)에서 DV 샘플이 **정확히 0**. 오탐이 없다는 뜻이므로 위 수치를 baseline noise 보정 없이 그대로 쓸 수 있다.
리더 경로도 6개 프로파일 전부 `batch=(450~8,294), row=0` — **전부 벡터화 경로**이며, 겨냥한 `ColumnarBatchUtil`이 맞다.

### 프로파일이 F-001의 기전을 그대로 보여준다

`sparse_c1`의 hot frame:

```
  5.28%  ColumnarBatchUtil.buildRowIdMapping          <- 겨냥한 그 루프
  1.94%  ...roaringbitmap.Util.hybridUnsignedBinarySearch  <- array 컨테이너 이진 탐색
  0.33%  ...roaringbitmap.RoaringBitmap.contains
  0.02%  ...roaringbitmap.ArrayContainer.contains
```

`run_c1`은 대신 `RunContainer.hybridUnsignedInterleavedBinarySearch`가 뜬다.
**컨테이너 타입이 바뀌면 프로파일에 뜨는 함수가 바뀐다** — F-001을 마이크로벤치가 아니라 실제 쿼리 프로파일에서 재확인한 것이다.

### 컬럼 수에 반비례한다 (예측대로)

1컬럼 40.37% → 20컬럼 3.75%. DV 체크는 행당 1회로 컬럼 수와 무관하므로 예측된 결과이며, 설계의 narrow/wide 양끝 측정이 옳았음을 뒷받침한다.
**따라서 "DV 체크가 스캔의 40%"는 조건부 주장이다. 반드시 "좁은 스캔에서"를 붙여야 한다.**

### wall-clock: 0.5%만 지워도 스캔이 13% 느려진다

| 조건 | median | `none` 대비 |
|---|---|---|
| `sparse` 1컬럼 | 0.309s | **+13.0%** |
| `sparse` 20컬럼 | 2.920s | −4.4% |
| `run` 1컬럼 | 0.218s | −20.3% |
| `run` 20컬럼 | 2.705s | −11.5% |

**전체의 0.5%만 삭제된 테이블이, 삭제가 전혀 없는 테이블보다 13% 느리게 스캔된다.** 내보낼 행이 0.5% 더 적은데도 그렇다.
반대로 `run`(30% 삭제)은 오히려 빨라진다 — 안 내보내는 행이 많아 하류 작업이 줄어드는 효과가 DV 체크 비용을 압도한다.

> ⚠️ wall-clock 차이는 DV 체크 비용만이 아니라 "삭제된 행을 안 내보내서 줄어든 하류 작업"도 포함한다. 인과 귀속은 프로파일 수치를 쓸 것. 여기서 wall-clock은 **방향과 크기의 감각**을 주는 보조 지표다.

### 이 수치의 한계

## F-007 · 계단은 실제 테이블에서도 살아남는다 — 전이 폭 0.30%p (2026-08-17)

**Phase 1의 핵심 질문에 대한 답: 그렇다.**

F-001의 "6.25% 경계에서 4.1배 점프"는 단일 청크를 통제한 마이크로벤치였다. 실제 테이블은 파일당 청크가 30개고 청크마다 카디널리티가 흔들리므로, 경계 부근에서 array와 bitmap이 섞여 **계단이 뭉개질 수 있었다.** 그게 이 프로젝트에서 가장 검증 안 된 가정이었다.

**전이 폭이 0.30%p다.** 0.05%~50%를 훑는 밀도 축에서 이건 사실상 수직선이다.
평균화로 뭉개질 거라는 우려는 기각됐다 — 청크 간 카디널리티 편차(sd≈61)가 임계값 대비 워낙 작아서, 밀도가 조금만 움직여도 청크 전체가 함께 넘어간다.

**즉 "삭제율에 따라 스캔 비용이 계단식으로 점프한다"는 표현은 실제 테이블에서도 정당하다.**

### 덤으로 나온 것 1 — 파일 끝 부분 청크

각 파일의 마지막 청크는 온전한 65536이 아니다. 200만 행 / 65536 = 30.5178이므로 청크 30의 용량은 **33,920 (51.8%)** 뿐이다.

그래서 이 청크만 `4096 / 33920 = 12.08%` 에서 bitmap으로 넘어간다. 실제로 d=12.00%까지 array로 남아 있다가 그 위에서 넘어갔다. 처음 분석에서 "4개 청크가 12%까지 array"로 보여 전이 폭이 5.9%p로 잘못 계산됐고, 청크 용량을 반영해 고쳤다.

**실무 함의**: 파일 행 수가 65536의 배수인 경우는 거의 없으므로, **모든 DV에는 임계값이 다른 청크가 하나씩 섞여 있다.**

### 덤으로 나온 것 2 — DV 크기가 밀도와 무관해지는 구간

`d ∈ [6.25%, 50%]` 에서 DV 바이트가 3% 이내로 동일하다 (994,346 → 1,015,808).

bitmap 컨테이너가 카디널리티와 무관하게 **8,192B 고정**이기 때문이다. 삭제 행당 비트로 보면:

| 0.05% | 4,156 | 11,071 | **21.31 bit** |
| 0.50% | 40,154 | 83,079 | 16.55 bit |
| 6.25% | 500,213 | 997,130 | 15.95 bit |
| 12.00% | 959,685 | 1,526,870 | 12.73 bit |
| 50.00% | 4,002,668 | 1,018,599 | **2.04 bit** |

**50%를 지우는 것이 6.25%를 지우는 것과 같은 바이트를 쓴다.** CPU 비용은 6.25% 위에서 싸지고, 저장 비용도 위에서 상대적으로 싸진다 — 두 축이 같은 방향을 가리킨다.

## F-008 · 밀도 → 비용 곡선: 톱니 모양 (2026-08-17, 2026-08-18 재측정)

**이 프로젝트의 핵심 그래프.** 실제 쿼리 프로파일에서 밀도를 스윕한 결과.

> ⚠️ **2026-08-18 갱신.** 최초 단일 측정본을 **3회 반복 측정으로 전부 교체**했다.
> 노이즈 바닥이 √n 추정(±6%)이 아니라 **중앙값 9.7% / 최대 25.9%** 였기 때문이다 (F-010).
> 아래 숫자는 모두 3회 평균이고, 범위를 같이 적었다. **범위가 겹치는 두 점의 차이는 주장하지 않는다.**

측정이 성립하는 근거: `buildRowIdMapping`은 배치마다 `batchSize`번 **무조건** 프로브한다. 밀도가 0.5%든 50%든 `contains()` 호출 횟수는 동일하고, 총 스캔 행 수도 800만으로 고정이다. 따라서 **DV 샘플 수를 그대로 비교하면 그게 곧 호출당 비용**이다. 별도 정규화가 필요 없다.

| d | 온전청크 array% | 평균 card | DV 샘플 (3회 평균) | 범위 | 흩어짐 | DV/스캔 | |
|---|---|---|---|---|---|---|---|
| 0.00% | — | 0 | **0** | 0–0 | — | 0.00% | 대조군, 오탐 없음 |

### 모양: 오르막 → 절벽 → (평평하지 **않은**) 저지대

1. **array 구간(d < 6.25%)에서 비용이 밀도와 함께 오른다.** 599 → 746 → 872.
   이진 탐색이 `O(log n)`이기 때문이다. F-001의 마이크로벤치(카디널리티 327 → 13.0ns, 3,276 → 16.0ns)와 방향과 크기가 일치한다.
   599 vs 872는 범위가 겹치지 않는다 (633 < 838). **유의.**
2. **경계에서 떨어진다.** 872 → 394, **2.22배.** 겹침 없음 (838 vs 406). **유의.**
3. **bitmap 구간은 평평하지 않다.** ← 단일 측정에서는 평평해 보였으나 **틀렸다.**

### 🔺 반복 측정이 뒤집은 것 ①: bitmap 구간의 반등

단일 측정본은 bitmap 구간을 `162 / 185 / 171 / 187` 로 읽고 "평평하다, 셋의 차이는 노이즈"라고 적었다. 3회 평균은 다른 그림을 준다:

| d | DV 샘플 | 범위 |
|---|---|---|
| 7.00% | **394** | 381–406 |
| 12.00% | 422 | 410–447 |
| 50.00% | **496** | 454–529 |

**394 → 496, 1.26배. 노이즈 바닥(9.7%)을 넘고 범위도 겹치지 않는다.** bitmap 구간에서 밀도가 올라가면 비용이 **다시 오른다.**

`BitmapContainer.contains`는 O(1)이므로 이건 컨테이너 조회 비용이 아니다. 가설 두 개:

- **분기 예측 실패.** `if (isDeleted(pos))` 의 분기 확률이 d=50%에서 정확히 최악이 된다. d=7%면 93% 확률로 한쪽이지만 d=50%면 예측 불가.
- **삭제된 행마다 추가 작업.** 삭제 분기는 `rowIdMapping` 쓰기를 건너뛰고 삭제 카운트를 올린다. 삭제 행이 많을수록 이 경로를 자주 탄다.

**둘 다 미확정이다.** 분기 실패율을 직접 재려면 PMU가 필요하다 → Phase 2 `.metal` (`-prof perfnorm`). 지금은 "bitmap 구간도 평평하지 않다"까지만 주장한다.

이 반등은 이야기를 오히려 **강화**한다. 최악은 경계 직전(d=6.1%)이고, 두 번째로 나쁜 곳은 고삭제율(d=50%)이며, **최적점은 경계 바로 위라는 아주 좁은 골짜기**다.

### 혼합 구간이 중간값을 준다

d=6.25%는 array 46.7% / bitmap 53.3% 혼합인데, DV 샘플 654가 **경계 아래(872)와 위(455) 사이에 위치**한다. 컨테이너 혼합 비율이 비용을 섞는다는 뜻이고, F-007의 컨테이너 곡선과 F-008의 비용 곡선이 같은 것을 보고 있음을 교차 검증해준다.

다만 6.40%(455)와 7.00%(394)의 차이는 15.5%로 노이즈 바닥 바로 위이고, 6.40%의 흩어짐이 25.9%(전체 최악)이다. **이 두 점의 순서는 주장하지 않는다.**

### 마이크로벤치보다 배율이 작은 이유

**공개할 때는 2.22배를 쓴다.** 4.1배는 "컨테이너 연산만 떼어내면"이라는 단서가 붙어야 한다.

### 🔺 반복 측정이 뒤집은 것 ②: "단조 감소"는 거짓이었다

단일 측정본은 `363 → 350 → 317 → 320 → 216 → 166 → 104`을 보고 **"nRuns가 줄면 싸진다는 예측대로 단조 감소한다"**고 적었다. 이건 틀렸다.

3회 평균에서 **L=1, 2, 4, 8은 서로 구분되지 않는다:**

```
L=1    596 ────────── 658
L=2         634 ─────────────────── 766
L=4  543 ──────────── 645
L=8              590 ── 620
     └────────── 전부 겹침 ──────────┘
```

그리고 **최대값은 L=2 (692)이지 L=1 (637)이 아니다.** 실질적인 비용 감소는 **L≥64 부터**만 일어난다:

| 구간 | 평균 nRuns | 비용 |
|---|---|---|
| L = 1 … 8 | 162 → 40 | **변화 없음** (전부 겹침) |
| L = 64 → 4096 | 4.7 → 1.0 | 428 → 180, **2.38배 감소** |

기전이 맞다: `RunContainer.contains`는 nRuns에 대한 이진 탐색이므로 비용은 `log₂(nRuns)`다. nRuns 162 → 40은 log₂로 7.3 → 5.3, 겨우 1.4배 — 노이즈에 묻힌다. nRuns 40 → 1은 5.3 → 0, 즉 **이진 탐색이 사라진다.** 실측 2.38배가 여기서 나온다.

**정정: 클러스터링의 이득은 완만하지 않다. 문턱이 있다.** run 길이를 2배, 4배 늘리는 건 CPU에 아무 도움이 안 되고, **청크당 run 개수가 한 자릿수로 떨어져야** 효과가 나온다.

### 🔺 그리고 그 자리에서 "공간 최적 ≠ 스캔 최적"이 실물로 잡혔다

L=2는 `runOptimize()`가 컨테이너를 바꾸는 정확한 경계다:

```
L=2, 평균 카디널리티 321, nRuns 162
  RunContainer   = 2 + 4×162 = 650 B
  ArrayContainer = 2 × 321   = 642 B    <- 청크마다 뒤집힘
                                          실제로 44 array / 76 run 으로 갈렸다
```

`runOptimize()`의 판단 기준은 **바이트뿐**이다. 빨라지는지는 보지 않는다. 그래서:

| | L=1 (array) | L=2 (run 76 / array 44) |
|---|---|---|
| DV bytes | 80,308 | 79,400 (**−1.1%**) |
| DV 샘플 | 637 (596–658) | 692 (634–766) |

**바이트는 줄었는데 비용은 안 줄었다** (범위가 겹치므로 "늘었다"고도 주장하지 않는다). 이유는 명확하다 — run이 162개면 `RunContainer.contains`는 여전히 이진 탐색이고, 탐색 대상 크기가 array(321)에서 run(162)로 절반이 된 건 log₂로 0.99밖에 안 줄어든다.

이건 README §4.2에 **"질문"으로만 적어두었던 항목**이고, 이제 답이 있다: **`runOptimize()`의 전환 임계값은 스캔 성능 관점에서 최적이 아니다.** 최적이려면 "바이트가 주는가"가 아니라 "nRuns가 한 자릿수로 떨어지는가"를 봐야 한다.

단, 이건 **Iceberg가 아니라 RoaringBitmap 라이브러리의 설계 결정**이고 라이브러리 입장에서는 이름 그대로 공간 최적화이므로 버그가 아니다. Iceberg 쪽 함의는 **"DV 크기를 보고 스캔 성능을 추정하지 말라"**는 것이다.

### `p`(청크 점유율)가 아직 얽혀 있다 — 미해결

| L | 컨테이너 개수 (전체 124 청크 중) |
|---|---|
| 1 | 124 |
| 64 | 120 |
| 512 | 68 |
| 4096 | **12** |

L이 커지면 삭제가 소수 청크에 뭉치므로 **컨테이너가 없는 청크가 늘어난다.** 이건 두 경로로 비용을 줄인다:

1. `RoaringArray` 최상위 이진 탐색 대상이 31개 → 3개로 축소
2. 컨테이너가 없는 청크의 position은 즉시 "삭제 아님" 판정

**즉 3.53배 중 얼마가 run 구조 덕이고 얼마가 `p` 감소 덕인지 아직 분리되지 않았다.** 분리 실험은 시도했고 **실패했다** — F-010 참조.

### 실무 번역 (정정본)

| 워크로드 | 대략의 L | 청크당 nRuns | 예상 |
|---|---|---|---|
| 랜덤 키 기준 삭제 | 1 | — (array) | 가장 비쌈 |
| 살짝 뭉친 삭제 | 2 ~ 8 | 수십~수백 | **CPU 이득 없음.** DV 크기만 최대 4배 감소 |
| 삭제 키로 정렬된 테이블 | 수백~수천 | 한 자릿수 | **비용 1/3.5, DV 크기 1/1000** |

**"삭제 대상 키로 클러스터링하라"에 처음으로 수치가 붙었고, 동시에 조건이 붙었다: 어중간하게 뭉치면 CPU 이득은 0이다.**

### 한계

## F-010 · 반복 측정 — 노이즈 바닥은 9.7%, √n 추정은 완전히 틀렸다 (2026-08-18)

**이 프로젝트에서 가장 값비싼 교훈.** 별도 항목으로 남긴다.

### 어떻게 발견했나

`p` 축 실험(`06-occupancy.sh`)을 돌리던 중 **같은 설정을 실수로 두 번 측정**하게 됐다:

| 설정 | 1차 | 2차 | 차이 |
|---|---|---|---|
| d=0.5% (밀도 축과 중복) | 303 | 363 | **20%** |
| p 축 중복 테이블 | 120 | 169 | **41%** |

F-008에서 나는 노이즈를 Poisson 근사 `±√n`으로 추정하고 "350 ± 19 이므로 명확히 분리됨"이라고 적었다. **±6% 추정에 실제는 20~41%였다.** 두 배가 아니라 **자릿수가 틀렸다.**

원인은 `ctimer` 샘플링 자체가 아니라 그 위에 얹힌 것들이다 — JIT 컴파일 시점, GC 타이밍, 샘플러 위상, WSL2 스케줄링. √n은 **샘플러가 완벽하고 대상이 고정이라는 가정**에서만 유효한데, 여기서 흔들리는 건 측정 대상 쪽이다.

### 대응

```
SCAN_ITERS  8 → 30     프로파일 1회 40초 중 ~30초가 JVM/Spark 기동이라
                       스캔 반복을 늘려도 벽시계는 거의 안 늘고 샘플만 는다
REPS        1 → 3      같은 설정을 완전히 독립된 JVM 3개에서 측정
```

15개 설정 × 3회 = **48회 프로파일, 698초.**

### 결과

```
흩어짐 (max−min)/mean :  중앙값 9.7%   최대 25.9%
```

**이 값보다 작은 차이는 주장하지 않는다**를 `aggregate.py`에 규칙으로 박아넣었다 (`verdict = "유의" if (ratio-1)*100 > noise`).

### 무엇이 살아남고 무엇이 죽었나

| 주장 | 단일 측정 | 3회 반복 | 판정 |
|---|---|---|---|
| 밀도 축 경계 전후 비용 점프 | 2.16배 | **2.22배** | ✅ 유지 (오히려 강화) |
| 클러스터링 L=1 → L=4096 | 3.49배 | **3.53배** | ✅ 유지 |
| DV/스캔 최대 점유 | 40.4% | **53.2%** | ✅ 유지 (강화) |
| bitmap 구간이 평평하다 | 평평 | **1.26배 반등** | ❌ **폐기** |
| 클러스터링이 단조 감소한다 | 단조 감소 | **L≤8 구간 구분 불가** | ❌ **폐기** |
| 인접 밀도 간 미세 구조 | 여러 개 | — | ❌ **전부 폐기** |

**큰 주장 셋은 전부 살아남았고 오히려 커졌다. 죽은 건 미세 구조뿐이다.** 다만 이건 사후적으로 운이 좋았던 것이지, 반복 없이 주장했던 방법이 옳았던 건 아니다.

### `p` 축 실험은 실패로 기록한다

F-009에 남은 L↔p 교란을 풀려고 밀도·L을 고정하고 점유 청크 수 `p`만 바꾸는 실험을 설계했다. **작동하지 않았다:**

- 삭제 술어가 `pmod(hash(chunk_idx, seed), 10000) < p`인데, 파일당 청크가 **30개뿐**이라 해시 선택의 해상도가 3.3%p 단위였다.
- 그 결과 **p=5%와 p=10%가 완전히 동일한 테이블**이 됐다. 서로 다른 두 설정을 만들고 있다고 믿으면서 같은 걸 두 번 잰 것이다 (위 "41% 차이" 쌍이 바로 이것이다).

제대로 하려면 `ROWS_PER_FILE`을 2M → 8M 이상으로 올려 파일당 청크를 **120개+**로 만들어야 한다. 그래야 p를 1%p 단위로 통제할 수 있다. 측정 시간은 4배가 된다.

**현재 상태: F-009의 3.53배는 "클러스터링의 총 효과"로만 주장 가능하고, run 구조 기여분과 컨테이너 개수 감소 기여분으로 나눌 수 없다.**

### 방법론 교훈 (다음 단계에도 적용)

1. **노이즈는 추정하지 말고 측정한다.** 같은 설정을 3회 돌리는 비용은 전체의 1/15이었다.
2. **격자를 만들 때 실제로 서로 다른 데이터가 나오는지 먼저 검증한다.** p 축은 이걸 안 해서 통째로 날아갔다.
3. **주장 임계값을 코드에 박는다.** 사람이 표를 보고 판단하면 반드시 노이즈를 신호로 읽는다.

**재현**: `phase1/scripts/07-remeasure.sh` — `phase1/results/summary.txt`, `summary.json`

## F-011 · Iceberg를 실제로 고쳤다 — 최악 지점에서 DV 체크 CPU 9.3배 감소 (2026-08-18)

**§7.1의 결정적 숫자.** 마이크로벤치가 아니라 **Iceberg 소스를 고쳐 빌드한 jar으로** 잰 결과다.

### 무엇을 했나

`apache-iceberg-1.11.0` 태그(커밋 `6976e02`)를 클론해 175줄을 고쳤다:

```
core   PositionDeleteIndex.forEachInRange(long, int, LongConsumer)   default = 현행 동작
       BitmapPositionDeleteIndex / EmptyPositionDeleteIndex          오버라이드
       RoaringPositionBitmap.forEachInRange                          RoaringBitmap 위임
spark  ColumnarBatchUtil                                             equality delete 없을 때 구간 경로
```

전체 diff와 작업 기록: [`upstream/`](../upstream/README.md), [`range-scan.patch`](../upstream/range-scan.patch)

### 🔺 이슈 초안의 전제가 틀렸다 — 빌드해보지 않았으면 못 잡았을 오류

초안은 빠른 경로를 `eqDeleteFilter == null`로 게이트하자고 썼다. 실제 코드는:

```java
// DeleteFilter.java:245
public Predicate<T> eqDeletedRowFilter() {
  ...
  eqDeleteRows = applyEqDeletes().stream()...orElse(t -> true);   // ← null 이 아니다
  return eqDeleteRows;
}
```

equality delete가 없어도 **`t -> true`를 돌려준다.** 초안대로 짰다면 빠른 경로는
**단 한 번도 실행되지 않았을 것이고**, 패치는 "정확하지만 효과 0"으로 측정됐을 것이다.

실제 게이트는 `!deletes.hasEqDeletes()`다. **이슈를 먼저 내지 않은 판단이 여기서 값을 했다.**

### 정확성 게이트가 먼저다

빨라졌는데 답이 다르면 의미가 없다. 성능 측정 전에 7개 테이블에서
`count(*)`, `sum(id)`, `min/max(id)`를 두 jar로 각각 계산해 대조했다.

## F-012 · 패치의 나머지 두 경로 — `buildIsDeleted` 18.9배, equality delete 회귀 없음 (2026-08-18)

F-011이 남긴 두 개의 "안 쟀다"를 채웠다.

- **A1** — equality delete가 있는 테이블. 패치는 이 경우 기존 행별 루프로 폴백한다.
  **"코드를 안 건드렸다"와 "안 느려졌다"는 다른 말**이다.
- **A2** — `buildIsDeleted` 경로. `buildRowIdMapping`과 같이 고쳤는데 측정을 안 했다.

### A2 · `_deleted` 투영 — 개선이 오히려 더 크다

`_deleted` 메타데이터 컬럼을 투영하면 리더가 다른 분기를 탄다
(`BaseBatchReader.filterBatch:141` → `hasIsDeletedColumn` → `buildIsDeleted`).
삭제 행을 **제거하는 대신 표시**하므로 8,000,000행이 전부 나온다.

| 설정 | baseline | patched | 개선 | DV/스캔 | 스캔 서브트리 | wall-clock |
|---|---|---|---|---|---|---|
| d=0.5% + `_deleted` | 649 (573–717) | **34 (25–42)** | **18.90배** | 43.7% → **3.8%** | −39.0% | 0.217 → 0.160s |
| d=6.1% + `_deleted` | 854 (793–892) | **57 (56–58)** | **14.90배** | 52.2% → **6.0%** | −41.7% | 0.205 → 0.159s |

범위가 압도적으로 분리된다. 가장 보수적으로 봐도 13.6배가 남는다.

**`buildRowIdMapping`(8.6배)보다 큰 이유**가 있고, 기전이 명확하다:

```
buildRowIdMapping  패치본:  삭제 위치 ~25개 방문 + 그 사이를 살아있는 행으로 채움
                            -> 배치당 rowIdMapping 쓰기 ~4,975회
buildIsDeleted     패치본:  삭제 위치 ~25개만 방문해서 isDeleted[i]=true
                            -> 배치당 쓰기 ~25회
```

`buildIsDeleted`는 **구간 순회의 이점을 온전히 받는다.** 빈틈을 채울 필요가 없기 때문이다.
삭제율이 낮을수록(0.5% → 18.9배 vs 6.1% → 14.9배) 격차가 더 벌어지는 것도 같은 이유다.

정확성도 확인했다. `count(*)`가 8,000,000 그대로이고, `_deleted`로 표시된 행 수가
DV 카디널리티와 **정확히 일치**했다 (40,154 / 488,161). 살아있는 행의 `id` 합도
일반 모드의 `sum(id)`와 바이트 단위로 같았다. 두 arm 모두.

### A1 · equality delete — 회귀 없음, 그리고 뜻밖의 음성 대조군

Spark 커넥터는 equality delete를 쓰지 못한다(DELETE는 항상 position delete/DV로 나간다).
Iceberg Java API(`Parquet.writeDeletes(...).buildEqualityWriter()`)로 직접 만들어
`RowDelta`로 커밋했다 — [`phase2/tools/AddEqualityDeletes.java`](../phase2/tools/AddEqualityDeletes.java).

| 테이블 | 구성 | 살아있는 행 |
|---|---|---|
| `eq0` | equality delete 40,000개만 (DV 없음) | 7,960,000 |
| `eq50` | DV 40,154개 **+** equality delete 40,000개 | 7,920,040 |

`eq50`의 7,920,040 = 8,000,000 − 40,154 − 40,000 + 겹침 194. **두 삭제 종류가 같은 테이블에서
동시에 살아 있다** — 패치의 게이트가 빠른 경로를 적극적으로 거부하는 유일한 경우다.

| 설정 | baseline | patched | 배율 | 판정 |
|---|---|---|---|---|
| `eq0` (음성 대조군) | 3,303 (2,590–4,249) | 2,635 (2,594–2,679) | 1.25배 | **범위 겹침 — 주장 불가** |
| `eq50` (게이트 거부) | 3,362 (3,177–3,559) | 3,524 (3,267–3,955) | 0.95배 | **범위 겹침 — 주장 불가** |

**결론: 회귀 없음.** 다만 `eq50`의 점추정은 5% 나빴다는 것을 그대로 적어둔다.
기전상 추가된 것은 배치당 `hasEqDeletes()` 호출 하나(`List.isEmpty()`)뿐이므로 노이즈로 본다.

### 🔺 `eq0`이 음성 대조군이 됐다 — 노이즈 천장을 실측했다

이건 설계한 게 아니라 결과를 보다가 알아챈 것이다. `eq0`에는 position delete가 없으므로:

```java
PositionDeleteIndex deletedPositions = deletes.deletedRowPositions();   // null
if (deletedPositions != null && !deletes.hasEqDeletes()) { ... }        // 즉시 단락
```

`deletedPositions == null`에서 단락되어 `hasEqDeletes()`는 **호출조차 되지 않는다.**
즉 `eq0`에서 두 arm은 **바이트 단위로 같은 코드를 실행한다.**

그런데 측정값은 **1.25배 차이**가 났다 (baseline 흩어짐 50.2%: 2,590 / ~3,070 / 4,249).

**동일한 코드가 1.25배의 겉보기 효과를 만들어낼 수 있다.** 이건 F-010의 노이즈 바닥(9.7%)이
샘플 수가 적거나 워크로드가 무거울 때 훨씬 커질 수 있다는 직접 증거이고, 동시에
**F-011의 8.6~9.3배와 A2의 14.9~18.9배가 그 천장보다 한 자릿수 위**라는 것을 보여준다.

우연히 얻었지만 이 프로젝트에서 가장 값싼 검증이었다.

### 한계

- **equality delete 테이블의 "DV 샘플"은 DV만이 아니다.** 분류기가 `org.apache.iceberg.deletes.*`를
  통째로 잡는데, equality delete 처리도 이 패키지에 있다. 그래서 `eq0`/`eq50`의 77~81%는
  "삭제 처리 전체"이지 "DV 체크"가 아니다. **arm 간 비교에는 문제없지만 절대값을 F-011의

- equality delete를 `id` 한 컬럼에만 걸었다. 다중 컬럼 equality delete는 미측정.
- `_deleted` 투영은 8M행을 전부 내보내므로 일반 스캔보다 무겁다. 두 arm이 같은 조건이라
  비교는 성립하지만, wall-clock을 F-011의 일반 스캔과 직접 비교하면 안 된다.

## F-013 · RUN 마이크로벤치 정정 — 3,992배는 퇴화값이었다. 정직한 숫자는 56~150배 (2026-08-18)

F-002의 `RUN` 열은 **배치 전체가 삭제되는 퇴화 케이스**였다. 청크의 35~65%를 통째로 삭제하고
배치를 그 한가운데 두었으므로, 배치의 5,000행이 **전부** 삭제된다. 그러면 구간 API가
벌크 콜백(`acceptAllPresent`) 한 번으로 끝내버려 배속이 터무니없이 커진다.

`RUN_PARTIAL` 패턴을 추가했다 — 길이 64 블록을 청크 전체에 균등 분포시켜 밀도 5%를 맞춘다.
블록 51개(간격 1,285)라 **run 컨테이너지만 nRuns가 51이고, 배치는 그중 약 4블록과 부분 겹침**한다.
F-009의 `L=64` 지점에 대응한다.

### 결과 (배치당 µs, JMH, batchSize 5,000)

| 패턴 | 컨테이너 | nRuns | 현행(행별) | `forAllInRange` | `forEachInRange` | 배속 |
|---|---|---|---|---|---|---|
| `MEDIUM_5` (d=5%) | array | — | 81.54 ± 5.6 | 1.81 ± 0.11 | 1.86 ± 0.29 | 45배 |
| **`RUN_PARTIAL`** (d=5%, L=64) | **run** | **51** | **44.67 ± 1.3** | **0.298 ± 0.016** | **0.800 ± 0.053** | **150배** |
| `RUN_CONTIG` (배치 전체 삭제) | run | 1 | 22.72 ± 0.9 | 0.006 ± 0.000 | 2.354 ± 0.072 | 3,787배 ⚠️ |

### 🔺 덤: F-009의 기전을 마이크로벤치에서 독립 확인했다

`MEDIUM_5`와 `RUN_PARTIAL`은 **밀도가 5%로 같다.** 삭제 행 수도, 살아남는 행 수도 거의 같다.
다른 것은 **컨테이너 구조뿐**이다.

```
array  카디널리티 3,277  ->  log₂ = 11.68   81.54 µs
run    nRuns         51  ->  log₂ =  5.67   44.67 µs
                                예측 배율 11.68 / 5.67 = 2.06배
                                실측 배율 81.54 / 44.67 = 1.83배   (오차 11%)
```

이진 탐색의 `O(log n)` 모델이 **밀도를 고정한 채** 재현됐다. F-009는 실제 쿼리 프로파일에서
클러스터링 효과를 봤고, 여기서는 통제된 마이크로벤치에서 같은 기전을 봤다. **두 층위가 일치한다.**

그리고 F-009가 말한 문턱도 같은 방향이다 — nRuns 51은 여전히 이진 탐색이라 array 대비
2배 안쪽에 머문다. 한 자릿수로 떨어져야 이진 탐색이 사라진다.

### 🔺 그리고 이건 이슈 초안의 주장을 약간 깎는다

초안은 "작은 API(`forEachInRange`)로 충분하다, `RelativeRangeConsumer`는 API 표면이 크다"고 썼다.
run 컨테이너에서는 그 차이가 작지 않다:

| 패턴 | `forAllInRange` | `forEachInRange` | 차이 |
|---|---|---|---|
| `SPARSE_0_5` | 0.470 | 0.473 | 없음 |
| `MEDIUM_5` | 1.811 | 1.858 | 없음 |
| `DENSE_12` | 2.953 | 3.384 | 1.15배 |
| **`RUN_PARTIAL`** | **0.298** | **0.800** | **2.68배** |
| `RUN_CONTIG` | 0.006 | 2.354 | 392배 |

**run 컨테이너에서 `forAllInRange`가 2.7배 빠르다.** 블록 사이의 빈 구간을 `acceptAllAbsent`로
한 번에 건너뛸 수 있기 때문이다. `forEachInRange`는 삭제 위치만 통보받으므로 그 정보를 못 쓴다.

다만 **절대값으로는 둘 다 현행 대비 56배 이상**이므로, "작은 API로도 이득의 대부분을 받는다"는
주장 자체는 유지된다. 이슈에는 **"run 컨테이너(=정렬된 테이블)에서는 큰 API가 2.7배 더
빠르다"는 수치를 명시**하고 메인테이너가 판단하게 하는 것이 정직하다.

### 한계

- `h_isDeleted_forEachInRange`의 `RUN_PARTIAL` 값(3.885 ± 1.565)은 오차가 커서 읽지 않는다.
  `RUN_CONTIG`(2.118 ± 1.941)도 마찬가지다. `isDeleted` 계열은 fork/반복을 더 늘려야 한다.
- 블록 길이를 64 하나만 봤다. nRuns를 축으로 스윕하면 `O(log nRuns)` 모델을
  직접 피팅할 수 있는데 아직 안 했다.

## F-014 · 배치 크기 축 — 결론은 20배 범위에서 흔들리지 않는다. 그리고 내 기전 모델이 틀렸다 (2026-08-30)

**왜 이 축인가.** "이 결과가 다른 환경에서도 유지되나"에 대한 가장 값싼 대리 측정이다.
배치 크기는 사용자가 설정으로 바꾸는 값이고(Iceberg 기본 5,000), 엔진마다 다르며,
패치의 기전에 직접 얽혀 있다. 여기서 결론이 뒤집히면 이식성 주장은 거기서 끝난다.

### 배관부터 확인했다

`--batch-size` 가 조용히 무시되면 스윕 결과가 전부 "차이 없음" 으로 나오고,
우리는 그걸 **"배치 크기는 영향이 없다"로 오독**하게 된다. 00-install-jar.sh 의 jar 폴백과
같은 종류의 함정이다. 그래서 먼저 극단값으로 탐침했다 (`05a-probe2.sh`, baseline jar, d610):

| batch-size | median |
|---|---|
| 1 | **1.089 s** |
| 5,000 | 0.334 s |
| 100,000 | 0.393 s |

배치 1에서 3.3배 느리다 — 옵션이 리더까지 확실히 도달한다.
(경로는 `SparkReadConf.parquetBatchSize()`: `.option("batch-size")` → 테이블 속성
`read.parquet.vectorization.batch-size` → 기본 5000. **세션 conf 는 없다.**)

부수 관찰: 100,000 이 5,000 보다 **느리다.** 컬럼 버퍼가 커져 캐시를 밀어내는 것으로 보이나
1회 3반복 탐침이라 주장하지 않는다.

### 반증 가능한 예측을 먼저 적었다

- **P1** baseline 의 DV 비용은 배치 크기에 무관하다 (행당 이진 탐색이므로)
- **P2** patched 의 DV 비용은 배치가 커질수록 내려간다 (배치당 고정 비용이 분산되므로)
- **P3** 따라서 speedup 은 배치 크기에 대해 단조 비감소

### 결과 (2 설정 × 3 배치 × 2 arm × 3 반복 = 36 프로파일, arm 교차, 613초)

**d=0.5% (array)**

| 배치 | baseline | patched | 개선 |
|---|---|---|---|
| 1,000 | 729 (700–754) | 82 (63–92) | 8.92배 |
| 5,000 | 665 (653–682) | 75 (59–89) | 8.86배 |
| 20,000 | 682 (657–706) | 68 (58–88) | 10.03배 |

**d=6.1% (array, 최악 지점)**

| 배치 | baseline | patched | 개선 |
|---|---|---|---|
| 1,000 | 941 (917–974) | 109 (101–115) | 8.63배 |
| 5,000 | 914 (865–958) | 114 (110–117) | 7.99배 |
| 20,000 | 979 (835–1,111) | 130 (113–147) | 7.51배 |

### 판정 — P1만 살았다

| | 결과 |
|---|---|
| **P1** baseline 평평 | **✅ 대체로 맞다.** d=6.1%에서 세 배치의 범위가 전부 겹친다(구분 불가). d=0.5%에서는 (1000, 5000) 한 쌍만 분리되지만 20,000에서 다시 올라가 **방향이 일관되지 않는다** |
| **P2** patched 는 배치가 클수록 싸진다 | **❌ 틀렸다.** 두 설정 모두 배치 간 범위가 전부 겹치고, 게다가 **방향이 서로 반대다** (d=0.5%는 82→68 하락, d=6.1%는 109→130 상승). 배치 크기 효과가 아니다 |
| **P3** speedup 단조 비감소 | **판정 불가.** 배치 간 speedup 이 서로 구분되지 않는다 |

### 🔺 데이터가 내 기전 모델을 고쳤다

P2를 세운 근거는 "패치본은 배치당 한 번만 순회하므로 고정 비용이 행 수에 분산된다"였다.
**이건 틀렸다.** 패치본도 살아남은 행마다 `rowIdMapping` 에 써야 하므로
(배치 5,000에 삭제 25행이면 약 4,975회 기록) **비용이 여전히 행 수에 선형**이다.
배치당 고정 비용(최상위 키 조회, 컨테이너 조회)은 그 옆에서 무시할 만하다.

즉 **두 arm 모두 O(행)이고, 패치가 없앤 것은 각 행의 `O(log n)` 이진 탐색이라는 인자다.**
그러면 비율은 배치 크기에 대해 **상수여야 하고**, 관측된 것이 정확히 그것이다.

고친 모델이 더 단순하고 P1까지 같이 설명한다. 원래 모델은 P1을 설명하지 못했다
(baseline 도 배치당 고정 비용이 있으므로 원 모델대로면 baseline 도 배치에 의존했어야 한다).

### 그래서 얻은 것

**배치 크기 1,000~20,000(20배 범위)에서 개선이 유지된다 — 보수적으로 잡아도 최소 5.68배.**

이건 이식성 주장에 직접 쓰인다. 배치 크기는 **사용자가 바꾸는 값**이고 엔진마다 다른데,
20배를 흔들어도 결론이 안 움직인다. "당신 환경 설정에서만 그런 것 아니냐"는 반론에 대한
첫 번째 실측 방어다.

### 방법론 메모 — 집계기의 판정 로직이 규칙을 어기고 있었다

처음 작성한 `batchsize.py` 는 **점 추정만 보고 단조성을 판정**했고,
그래서 `8.63 → 7.99 → 7.51` 을 "❌ 기전 설명이 흔들린다"로 출력했다.
그런데 이 세 값의 반복 범위는 전부 겹친다 — **순서 자체에 의미가 없다.**
F-010에서 배운 규칙을 도구에 안 박아둔 탓이다. 겹침 판정을 넣어 고쳤다.
(고치기 전 출력을 그대로 믿었으면 없는 현상을 설명하려 들었을 것이다.)

### 한계

- 두 설정(d=0.5%, d=6.1%) 모두 array 구간이다. bitmap·run 구간은 미측정.
- 100,000 이상은 탐침만 했고 반복 측정하지 않았다. 캐시 압박으로 U자가 될 가능성이 있다.
- 다른 조건(웜 캐시, 1컬럼, Zen 3)은 그대로다. 이 축 하나를 흔들었을 뿐이다.

**재현**: `phase2/scripts/05a-probe2.sh` → `05-batchsize.sh` → `tools/batchsize.py`
