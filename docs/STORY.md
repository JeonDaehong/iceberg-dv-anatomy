> Apache Iceberg V3 의 deletion vector 읽기 경로를 뜯어 **문제를 찾고, 고치고, 그 결과가
> 내 노트북 밖에서도 성립하는지 확인한** 기록.

> 이 문서는 **서사**다. 40개의 발견을 시간순으로 쌓아둔

**한 문단 요약** — Iceberg V3 의 벡터화 리더는 배치의 **모든 행에 대해** 삭제 여부를
한 번씩 묻는다(`ColumnarBatchUtil.buildRowIdMapping`). 삭제가 0.5%뿐이어도 800만 번을
다 묻는다. 측정해보니 이 체크가 **좁은 스캔에서 스캔 CPU 의 43~58%** 를 차지했고,
행 단위 프로브를 **구간 단위 API 로 바꾸자 최악 지점에서 9.28배**, `_deleted` 투영
경로에서 **18.9배** 싸졌다. 그 결과는 CPU 3종·스토리지 2종·병렬도 16배·분산 클러스터에서
모두 유지됐다. 다만 **넓은 투영에서는 사라지고**(손익분기는 "DV 체크가 스캔 CPU 의 20% 이상"),
비용의 정체는 분기 예측도 캐시도 아닌 **행마다 호출한다는 구조 그 자체**였다.

## 1. 왜 했는가

### 1.1 Deletion vector 가 무엇인가

Iceberg 는 데이터 파일을 **불변**으로 다룬다. 행 하나를 지우려면 파일 전체를 다시 쓰거나,
"이 행은 지워졌다"는 **별도의 표시**를 남겨야 한다. 후자가 merge-on-read 다.

- **V2** 는 이걸 *positional delete file* 로 했다. `(파일 경로, 행 위치)` 쌍을 담은
  Parquet 파일이고, 삭제할 때마다 새 파일이 하나씩 생긴다. 파일이 수천 개로 불어난다.
- **V3** 는 이걸 **deletion vector** 로 바꿨다. 데이터 파일 하나당 **RoaringBitmap 하나**를
  Puffin 포맷에 담는다. 파일 수가 데이터 파일 수를 넘지 않고, 크기도 훨씬 작다.

**저장 측면에서는 명백한 개선이다.** 이 프로젝트가 묻는 것은 그다음이다 —
**읽을 때는?**

### 1.2 읽기 경로에서 무슨 일이 일어나는가

Spark 가 Iceberg 테이블을 벡터화 모드로 읽으면, Parquet 를 5,000행짜리 `ColumnarBatch`
단위로 디코딩한다. 삭제가 있으면 그 배치에서 지워진 행을 걷어내야 하는데, 그 일을 하는 것이
`ColumnarBatchUtil` 이다. 구조를 줄이면 이렇다:

```java
// ColumnarBatchUtil.buildRowIdMapping — 살아남은 행의 인덱스를 모은다
int[] mapping = new int[batchSize];
int live = 0;
for (int rowId = 0; rowId < batchSize; rowId++) {
    long pos = batchStart + rowId;
    if (!deletes.isDeleted(pos)) {      // ← 행마다 한 번씩 묻는다
        mapping[live++] = rowId;
    }
}
```

**핵심은 `if` 안쪽이 아니라 루프 자체다.** 삭제율이 0.5% 든 50% 든
`isDeleted(pos)` 호출 횟수는 **언제나 배치 크기와 같다.** 800만 행 테이블이면
삭제가 4만 행뿐이어도 800만 번 묻는다.

그리고 `isDeleted(pos)` 한 번은 공짜가 아니다. `RoaringPositionBitmap.contains(long)` 은
`long` 위치를 (상위 32비트 키, 하위 16비트) 로 쪼개고 → 키 배열을 이진 탐색해 컨테이너를 찾고
→ 2단 간접을 거쳐야 비로소 비트를 만진다.

### 1.3 왜 이게 문제라고 의심했는가

RoaringBitmap 은 **구간 단위 API** 를 이미 갖고 있다 — `forAllInRange`, `forEachInRange`,
`getBatchIterator`, `rangeCardinality`. 배치의 위치는 `[batchStart, batchStart+batchSize)`
라는 **연속 구간**이다. 즉 한 번의 구간 순회로 끝날 일을 5,000번의 개별 조회로 하고 있다.

특히 **삭제가 하나도 없는 배치**조차 5,000번을 다 묻는다. 구간 API 라면 O(1) 이다.

여기까지가 **코드를 읽고 세운 가설**이다. 이 프로젝트의 첫 번째 규율은
*"가설은 가설이라고 적고, 재기 전에는 주장하지 않는다"* 이다.

### 1.4 이 프로젝트가 스스로에게 건 규율

측정 프로젝트는 원하는 답을 찾기 쉽다. 그래서 규칙을 코드에 박아뒀다.

| 규칙 | 왜 | 어디에 박혀 있나 |
|---|---|---|
| **예측을 측정 전에 적고 커밋한다** | 나중에 판정 기준을 슬쩍 바꾸는 걸 막는다 | 각 `scripts/NN-*.sh` 헤더 |
| **채점 도구는 예측을 복제하지 않는다** | 두 곳에 있으면 한쪽만 고칠 수 있다 | `tools/*.py` 주석 |
| **반복 측정 범위가 겹치면 차이를 주장하지 않는다** | 노이즈를 발견으로 착각하는 걸 막는다 | 모든 채점기 |
| **REPS ≥ 3, arm 순서는 라운드마다 교대** | 머신 상태 표류가 arm 차이로 둔갑하는 걸 막는다 | 모든 측정 스크립트 |
| **게이트는 로그가 아니라 산출물을 본다** | "완료" 메시지는 거짓말을 한다 | 스크립트 게이트 |
| **실측 없이 업스트림에 내지 않는다** | 초안의 전제가 실제로 틀렸던 적이 있다 | 프로젝트 원칙 |

이 규칙들은 장식이 아니다. **아래 [10장](#10-내가-틀린-것들)에 이 규칙들이 실제로
잡아낸 것들을 전부 모아뒀다.**

## 2. 무엇을, 왜 실험했는가 — 설계와 규율

### 2.1 축 설계 — (d, C, p) 격자

가설이 맞다면 비용은 **RoaringBitmap 이 어떤 컨테이너를 고르느냐**에 달려 있다.
Roaring 은 64K 짜리 "청크" 마다 컨테이너를 따로 고른다:

| 컨테이너 | 조건 | 표현 | 조회 |
|---|---|---|---|
| **array** | 카디널리티 ≤ 4096 | 정렬된 `char[]` | 이진 탐색 O(log n) |
| **bitmap** | 카디널리티 > 4096 | 8KB 고정 비트셋 | O(1) 비트 테스트 |
| **run** | 연속 구간이 적을 때 | `(시작, 길이)` 목록 | 이진 탐색 |

카디널리티 4096 은 청크 밀도로 **4096/65536 = 6.25%** 다. 그래서 세 축을 잡았다:

- **`d`** — 삭제 밀도. 6.25% 경계를 가로지르게 촘촘히 스윕한다.
- **`C`** — 클러스터링(평균 run 길이 `L`). 밀도는 고정하고 삭제가 얼마나 뭉쳐 있는지만 바꾼다.
- **`p`** — 점유 청크 비율. 밀도와 `L` 을 고정하고 "삭제가 있는 청크가 몇 개냐"만 바꾼다.

> **왜 3점 설계가 아니라 스윕인가**: 원안은 A/B/C 세 지점만 잴 생각이었다. 그랬다면
> 6.25% 경계를 건드리지 못했을 것이다. 실제로 이 경계가 이 프로젝트에서 제일 중요한
> 발견이 됐다 ([F-001](findings.md), [F-007](findings.md)).

### 2.2 측정 방법과 그 한계

- **프로파일러**: async-profiler 4.5, `ctimer` 이벤트 (CPU 시간 기반 샘플링).
  스택에 DV 프레임이 있으면 그 샘플을 DV 로 귀속하는 **inclusive 집계**다.
- **분모 두 개**: `DV/전체`(JVM 기동·JIT·GC 포함, 보수적) 와 `DV/스캔`(리더 서브트리 안).
  게이트 판정은 보수적인 쪽을 썼다.
- **왜 CPU 시간인가**: I/O 대기가 분모에 안 들어간다. 이게 나중에
  [F-019](findings.md) 에서 "콜드 캐시로 바꿔도 비중이 안 움직인다"는 결과의 원인이 된다.
- **환경**: Spark 4.0.4 / Iceberg 1.11.0 / JDK 17 / WSL2 Ubuntu 24.04 / AMD Zen 3,
  `local[4]`, 8M 행 × 20컬럼 × 4파일.

### 2.3 노이즈를 먼저 쟀다

"차이가 있다"고 말하려면 **차이 없음이 얼마나 흔들리는지**를 먼저 알아야 한다.
같은 설정을 15개 × 3회 반복해서 **노이즈 바닥 = 중앙값 9.7%, 최대 25.9%** 를 확정했다
([F-010](findings.md)).

이게 없었다면 아래 여러 결과를 잘못 읽었을 것이다. 실제로 반복 측정이
**단일 측정본의 결론 두 개를 뒤집었다** ([10장](#10-내가-틀린-것들) 참조).

> 나중에 밝혀진 것: 9.7% 는 **워크로드가 아니라 내 WSL2 개발 환경의 성질**이었다.
> 전용 EC2 인스턴스에서는 7.0~12.7% 였다 ([F-020](findings.md)).

## 3. 결과 ① 진단 — 문제가 실재하는가

### 3.1 컨테이너 경계는 실재한다

먼저 파서를 만들어 Puffin 파일에서 컨테이너 타입을 직접 읽었다
([F-004](findings.md), [F-006](findings.md)). 그리고 실제 테이블에서 경계를 확인했다:

**전이 폭이 0.30%p 다** ([F-007](findings.md)). 청크 밀도 6.10% 에서는 거의 다 array,
6.40% 에서는 거의 다 bitmap 이다. 이항분포로 예측한 전이 곡선과 **3.7%p 이내로 일치**했다.
즉 이건 우연이 아니라 구조다.

### 3.2 컨테이너 타입이 비용을 4배 가른다 — 그리고 방향이 직관과 반대다

같은 5,000행 배치에 현행 경로(`contains()` 행당 1회)를 마이크로벤치로 재봤다
([F-001](findings.md)):

| 청크 밀도 | 카디널리티 | 컨테이너 | 배치당 | 행당 |
|---|---|---|---|---|
| 0.5% | 327 | array | 64.99 µs | 13.0 ns |
| **5%** | 3,276 | **array** | **80.22 µs** | **16.0 ns** |
| **12%** | 7,864 | **bitmap** | **19.76 µs** | **4.0 ns** |
| 연속 30% | 19,661 | run | 23.15 µs | 4.6 ns |

**삭제를 더 많이 할수록 체크가 싸진다.** 경계를 넘는 순간 행당 16.0ns → 4.0ns 로
**4.1배** 떨어진다.

함의가 반직관적이라 중요하다. *"삭제를 조금만 하면 싸다"* 가 아니다.
**삭제율 0~6.25% 구간 전체가 행당 비용이 가장 비싼 영역**이고, 실무 CDC 워크로드는
대부분 여기 있다.

### 3.3 실제 쿼리에서도 살아남는다 — 톱니 곡선

마이크로벤치가 아니라 실제 Spark 스캔에서 밀도를 스윕했다 ([F-008](findings.md)).
`contains()` 호출 횟수는 밀도와 무관하게 800만으로 고정이므로, **DV 샘플 수를 그대로
비교하면 그게 곧 호출당 비용**이다.

| 밀도 | 컨테이너 | DV 샘플 | 범위 | DV/스캔 |
|---|---|---|---|---|
| 0.50% | array 100% | 599 | 576–633 | 44.19% |
| **6.10%** | array 대부분 | **872** | — | **최악 지점** |
| 6.25% | array/bitmap 혼합 | 654 | 617–702 | 46.21% |
| 8% | bitmap | 394 | — | — |
| **50%** | bitmap 100% | **496** | 454–529 | 39.58% |

두 가지가 나왔다:

1. **경계 전후 2.22배.** 최악은 경계 **직전**(d=6.10%)이다.
2. **bitmap 구간이 평평하지 않다.** d=8% → 50% 에서 **1.26배 다시 오른다**
   (394 → 496, 범위 안 겹침). 이걸 "반등"이라 부르고 [9장](#9-기전--왜-비싼가)에서 다시 다룬다.

### 3.4 클러스터링은 밀도와 독립적으로 3.53배를 가른다

밀도를 d=0.5% 로 **고정**하고 평균 run 길이 `L` 만 스윕했다 ([F-009](findings.md)).
삭제 행 수가 같고 호출 횟수도 같으므로 남는 차이는 **컨테이너 쪽**뿐이다.

> ⚠️ 처음에 여기 "남는 차이는 컨테이너 **구조**뿐" 이라고 적었는데 **틀렸다.**
> `L` 을 키우면 삭제가 소수 청크에 몰려 컨테이너 **개수**도 같이 줄어든다(124 → 12개).
> 두 효과를 가른 것은 한참 뒤인 [F-036](findings.md) 이고, 답은 **개수 쪽이 주범**이었다.
> 아래 §3.4.1 로 이어진다.

| L | 컨테이너 | DV 샘플 | 범위 | DV bytes |
|---|---|---|---|---|
| 1 | array | 637 | 596–658 | 80,308 |
| 4096 | run | **180** | 177–185 | **72** |

**비용 3.53배, 저장 1,115배.** 범위가 압도적으로 분리된다. 이게 나중에
[8장의 처방](#8-결과--처방--패치를-기다리는-동안-할-수-있는-것)의 근거가 된다.

### 3.4.1 그런데 그 3.53배의 주범은 'run 구조' 가 아니었다

위 통제에는 구멍이 있었다. `L` 을 키우면 컨테이너 **타입**(array → run)과
**개수**(124 → 12)가 **같이** 움직인다. 어느 쪽이 값을 낸 것인지 갈리지 않는다.

가르려면 개수만 따로 움직이는 축이 필요하다. 밀도를 그대로 두고 **삭제가 있는 청크의
비율 `p`** 만 줄이면 컨테이너 개수는 줄지만 타입은 array 그대로다.
이 축은 [F-010](findings.md) 에서 한 번 통째로 날아갔다 — 파일당 청크가 30개뿐이라
`p` 를 바꿔도 **같은 테이블**이 나왔고, 그걸 모른 채 같은 걸 두 번 쟀다.
파일당 청크를 122개로 늘려 다시 쳤다 ([F-036](findings.md)):

| p | 컨테이너 | 타입 | DV 샘플 | 범위 |
|---|---|---|---|---|
| 100% | 492 | array | **2,564** | 2,482 ~ 2,598 |
| 50% | 256 | array | 1,911 | 1,769 ~ 1,941 |
| 25% | 136 | array | 1,560 | 1,273 ~ 1,628 |
| 10% | 68 | array | **1,156** | 985 ~ 1,224 |

**타입을 하나도 안 바꾸고 개수만 7.2배 줄였는데 2.22배가 나왔다.** 예측은 1.5배 미만이었다.

| | 컨테이너 감소 | 비용 이득 |
|---|---|---|
| F-009 `L=1 → L=4096` (구조 + 개수) | 10.3배 | **3.53배** |
| F-036 `p=100% → 10%` (개수만) | 7.2배 | **2.22배** |
| 나머지 (run 구조 몫) | — | **≈ 1.59배** |

**정렬이 좋은 이유는 run 컨테이너가 되어서가 아니라, 삭제가 있는 청크를 비우기 때문이다.**
[§8.2 의 "어중간하게 뭉치면 손해"](#82-처방에는-조건이-세-개-붙는다)와 같은 이야기다 —
run 이 되는 것 자체는 이득이 아니었다.

### 3.5 게이트 — 이걸 계속할 가치가 있는가

Phase 0 의 판정 기준은 "DV 체크가 스캔 CPU 의 5% 이상"이었다. 결과는
**40%** ([F-005](findings.md)). 게이트 **GO**.

음성 대조군도 뒀다 — DV 가 없는 테이블에서 DV 샘플이 **정확히 0** 이었다.
오탐이 없다는 뜻이므로 위 수치를 보정 없이 쓸 수 있다.

그리고 **벽시계로도 보인다**: 0.5% 만 삭제해도 스캔이 **+13%** 느려진다.

## 4. 개선하려면 어떤 방법이 있는가

### 4.1 근본 — 행 단위 프로브를 구간 단위로

RoaringBitmap 이 이미 갖고 있는 API 로 대안 5개를 마이크로벤치했다 ([F-002](findings.md)):

| 방법 | API | 개선 |
|---|---|---|
| `forAllInRange` + RelativeRangeConsumer | 구간을 훑으며 present/absent 를 통보 | **6~146배** |
| `forEachInRange` | 삭제된 위치만 방문 | 큰 개선 |
| `getBatchIterator` | 배치 단위 반복자 | 큰 개선 |
| `rangeCardinality` 빠른 경로 | 구간에 삭제가 0개면 O(1) 종료 | 빈 배치에 결정적 |

핵심은 `acceptAllAbsent` / `acceptAllPresent` **벌크 콜백**이다. run 컨테이너나
삭제가 없는 구간을 O(1) 로 처리한다.

> 이 숫자에는 정정이 붙는다. 처음 3,992배라고 적었던 RUN 케이스는 **배치가 통째로
> 삭제되는 퇴화 조건**이었다. 정직한 값은 **56~150배** 다 ([F-013](findings.md)).

### 4.2 대안 — 테이블 레이아웃 (사용자가 오늘 할 수 있는 것)

패치가 업스트림에 들어가 릴리스로 풀리기까지는 시간이 걸린다. 그동안 사용자가 할 수 있는
일이 없으면 이 프로젝트는 절반만 쓸모 있다.

[F-009](findings.md) 가 힌트를 줬다 — 삭제가 뭉쳐 있으면 컨테이너가 run 이 되고 3.53배 싸진다.
그렇다면 **삭제 키로 테이블을 정렬해두면** 실제로 그 효과가 날까? 이건 [8장](#8-결과--처방--패치를-기다리는-동안-할-수-있는-것)에서 잰다.

## 5. 어떻게 개선했는가

### 5.1 실제 Iceberg 를 고쳤다

마이크로벤치의 6~146배는 "이론상 가능"일 뿐이다. **Iceberg 를 실제로 패치하고 같은
방법으로 다시 쟀다** ([F-011](findings.md)).

고친 곳은 세 경로다:

| 경로 | 하는 일 | 고친 방식 |
|---|---|---|
| `buildRowIdMapping` | 삭제된 행을 걷어내고 살아남은 행의 인덱스를 모은다 | 구간 API 로 교체 |
| `buildIsDeleted` | `_deleted` 메타데이터 컬럼을 채운다 | 구간 API 로 교체 |
| equality delete | 술어 기반 삭제 | **건드리지 않는다** — 게이트로 기존 루프에 폴백 |

### 5.2 정확성을 먼저 검증했다

성능 개선이 결과를 바꾸면 아무 의미가 없다. 패치 전후로:

- 살아남은 행 수가 정확히 같은지
- `_deleted` 컬럼 값이 정확히 같은지
- equality delete 테이블에서 **회귀가 없는지**

전부 확인했다. equality delete 경로는 게이트가 **기존 루프로 정확히 폴백**하는 것을
확인했고, 이건 덤으로 **음성 대조군** 역할도 했다 — 패치가 안 닿는 경로에서는
개선이 안 나와야 하고, 실제로 안 나왔다 ([F-012](findings.md)).

### 5.3 같은 jar, 같은 바이트로 비교했다

두 arm 은 **md5 로 검증한 jar 쌍**이고, 테이블 바이트도 같다. 라운드마다 arm 순서를
교대해서 머신 상태 표류가 한쪽에 몰리지 않게 했다.

## 6. 결과 ② 개선 — 얼마나 좋아졌는가

### 6.1 헤드라인

| 경로 | 조건 | 개선 |
|---|---|---|
| `buildRowIdMapping` | 최악 지점 (d=6.10%) | **9.28배** ([F-011](findings.md)) |
| `buildIsDeleted` | `_deleted` 투영 | **18.9배** ([F-012](findings.md)) |
| equality delete | — | **회귀 없음** (의도된 폴백) |

`buildIsDeleted` 가 더 큰 이유는 빈틈을 채울 필요가 없어서다 — 살아남은 행을 앞으로
당기는 작업이 없다.

#### 밀도 전 구간 (2026-09-08 추가)

처음엔 d=0.5 / 6.1 / 7.0% 세 점만 쟀다. 전부 경계 근처라 **삭제가 많은 테이블에서
어떻게 되는지** 답이 없었다. 반등 구간을 채웠다 ([F-039](findings.md)):

| d | 컨테이너 | 개선 배율 |
|---|---|---|
| 0.5% | array | **8.56배** |
| **6.1%** | array (경계 직전) | **9.28배** |
| 7.0% | bitmap | 3.73배 |
| 8.0% | bitmap | 3.51배 |
| **50.0%** | bitmap | **2.60배** ← 하한 |

**어디서도 손해가 아니고, 최대 수혜 구간이 정확히 현행의 최악 지점이다.**
고삭제율에서 이득이 주는 이유는 분명하다 — 벌크 API 의 이점은 "삭제 사이의 빈 구간을
한 번에 건너뛴다" 에서 오는데, d=50% 면 삭제 사이 간격이 평균 1행이라 건너뛸 게 없다.
그래도 2.60배가 남는 것은 **행마다의 조회와 분기가 사라지기 때문**이다.

### 6.2 그런데 경계가 있다 — 넓은 투영에서는 사라진다

20컬럼을 투영하면 DV 체크 CPU 는 여전히 **6.33배** 줄지만,
**벽시계 차이는 주장할 수 없다** ([F-015](findings.md)). DV 비중이 4.8% 로 떨어져
노이즈에 묻히기 때문이다.

그래서 "**언제 이 개선이 보이는가**"를 따로 쟀다:

1. **손익분기는 컬럼 수 5~10개 사이** ([F-016](findings.md)) — 라고 처음엔 적었다.
2. 그런데 컬럼 타입을 통제해보니 **컬럼 수 가설이 죽었다** ([F-017](findings.md)):
   정수 10개(21.6%) > 문자열 3개(10.6%). 3/3 밀도에서 방향이 반대였다.
   **md5 문자열 컬럼 1개 = 정수 컬럼 8~10개어치.**
3. 문자열 길이를 통제하니 답은 **둘 다**였다 ([F-025](findings.md), [F-030](findings.md) 정정 후):
   `비용 = 1,808 + 61.6 × 길이` (R² = 0.95). 컬럼 고정비와 바이트당 비용이 둘 다 실재한다.
4. 결국 **진짜 축은 하나의 숫자**였다 ([F-018](findings.md)):
   `wall 절감 = 0.53 × 샘플 절감` 이라는 24점 회귀에서, 손익분기는
   **"DV 체크가 스캔 CPU 의 21% 이상"** 이다. 컬럼 수도 타입도 그 비중을 정하는 입력일 뿐이다.

> 이 0.53 이라는 보정 계수의 정체는 한참 뒤에야 밝혀진다 → [9.5](#95-보정-053-의-정체는-jit-이었다).

### 6.3 배치 크기를 바꿔도 결론이 흔들리지 않는다

배치 크기를 1,000 ~ 20,000 (20배 범위) 로 스윕해도 **최소 5.68배**가 유지됐다
([F-014](findings.md)). 다만 여기서 **내 기전 모델이 틀렸다는 걸 발견하고 고쳤다**
([10장](#10-내가-틀린-것들) 참조).

## 7. 결과 ③ 이식성 — 내 기계 밖에서도 성립하는가

여기까지는 전부 **한 대에서** 나왔다 — WSL2, Zen 3, 로컬 NVMe, `local[4]`, 웜 캐시.
"현업에게 유용하려면" 이게 환경을 타면 안 된다. 그래서 **같은 jar(md5 검증)과 같은 테이블
바이트**로 여섯 축을 따로 쟀다. 바뀌는 것이 한 번에 하나가 되도록 나머지는 전부 고정했다.

| 축 | 무엇을 바꿨나 | DV/스캔 비중 | 판정 |
|---|---|---|---|
| **페이지 캐시** | 웜 → 콜드 | 51.2% → **52.0%** | 안 움직인다 ([F-019](findings.md)) |
| **CPU** | Zen 3 / Sapphire Rapids / Graviton3 | 49.4% / 56.2% / 54.3% | ±7%p 안 ([F-020](findings.md)) |
| **스토리지** | EBS → S3 | 56.2% → **58.0%** | 오히려 +1.9%p ([F-021](findings.md)) |
| **병렬도** | `local[1]` → `local[16]` | 스프레드 1.7%p | 자릿수 안 바뀜 ([F-022](findings.md)) |
| **셔플** | 스캔만 → `GROUP BY` | 스캔 내 54% → 43% | 밴드 유지 ([F-024](findings.md)) |
| **분산 클러스터** | 단일 JVM → 3노드 | 54% → **41.6%** | 하한 ([F-027](findings.md)) |

**결론: 43~58% 밴드는 환경 독립이다.** 그리고 실무 판정 기준은
**"DV 체크가 스캔 CPU 의 20% 안팎이면 이 패치가 벽시계로 보인다"** 이고,
병렬도 보정은 `1.30 × N^0.141` 로 아주 완만하다.

### 7.1 예상 못 한 부수 결과들

- **콜드 캐시가 비중을 안 바꾸는 이유**: `ctimer` 가 CPU 시간이라 **I/O 대기가 분모에
  안 들어간다**. 스토리지는 "벽시계 중 CPU 비율"을 바꾸지 "CPU 중 DV 비율"을 안 바꾼다.
- **S3 가 비중을 안 바꾸는 이유**: S3 클라이언트의 자체 CPU(HTTP·TLS·체크섬)가
  전체의 **1.4%p** 뿐이다. 분모를 못 움직인다.
- **패치가 최신 CPU 에서 더 잘 든다**: 클라우드 인스턴스에서 11.3~17.9배 vs 내 기계 8.6~9.3배.
- **노이즈 바닥 9.7% 는 워크로드가 아니라 내 개발 환경의 성질이었다** —
  전용 인스턴스에서는 7.0~12.7%, 내 WSL2 는 중앙값 27.2%.

### 7.2 분산 클러스터에서는 42% 로 내려앉는다

3노드 Spark standalone(8코어, S3 테이블, **익스큐터**에 프로파일러 부착)에서:

| 쿼리 | DV/스캔 | 패치 배율 | 벽시계 |
|---|---|---|---|
| 스캔, 단일 JVM | 53.95% | 6.8배 | — |
| **스캔, 클러스터** | **41.58%** | **5.30배** | **−9.5%** (0/6 페어, p=0.03) |
| 집계, 클러스터 | 41.57% | 5.07배 | +0.7% (노이즈 안) |

익스큐터 기동·태스크 직렬화·S3 읽기가 전부 스캔 서브트리 안으로 들어와 분모를 키운다.
**58% 상단은 단일 JVM 조건**이었다.

**단, 8M행/8코어는 클러스터가 단일 JVM보다 2.3배 느릴 만큼 작다.** 고정비가 지배하므로
42% 는 **하한**으로 읽어야 한다.

그리고 벽시계 −9.5% 는 **분산 환경에서 지연시간 차이를 주장한 첫 사례**다.

## 8. 결과 ④ 처방 — 패치를 기다리는 동안 할 수 있는 것

### 8.1 삭제 키로 정렬하면 2.80배

**같은 행을 지운** 두 테이블(동일 술어, 행 단위로 검증: 양쪽 430,575행)을 놓고
정렬 여부만 바꿨다. 스캔 쿼리에 **술어를 안 걸어** 파일 스킵을 원천 차단했다 —
그래야 "정렬의 전체 이득"이 아니라 **그중 DV 몫**만 잰다 ([F-023](findings.md)).

| | DV 체크 CPU | DV/스캔 | baseline 대비 |
|---|---|---|---|
| 무정렬, 무패치 | 915 | 51.0% | 1.0배 |
| **정렬, 무패치** | 327 | 27.3% | **2.80배** |
| 무정렬, 패치 | 117 | 10.9% | 7.8배 |
| **정렬 + 패치** | 74 | 8.0% | **12.39배** |

기전이 파일에 보인다: 무정렬은 모든 청크가 ~7,000바이트 array, 정렬은 6~10바이트 run 이고
DV 전체가 **864KB → 2.5KB** 로 준다. 비-DV 스캔 샘플은 876 vs 883 으로 같다 —
**통제가 살아 있다는 증거**다.

### 8.2 처방에는 조건이 세 개 붙는다

**조건 1 — 삭제가 소수 키 값에 몰릴 때만** ([F-026](findings.md)):

| 정렬 키 고유값 | 값당 행 수 | DV 체크 이득 |
|---|---|---|
| ~1,000 | ~8,000 | **2.78배** |
| ~1,000,000 | ~8 | 1.10배 |
| ~10⁹ (사실상 유일) | 1 | **0.89배** |

날짜·지역·테넌트로 지우면 좋은 조언이고, **행 ID 로 흩어 지우면 아무 조언도 아니다.**

**조건 2 — 삭제율이 경계 아래일 때만 크다** ([F-035](findings.md)).
경계 **위**(d=12%)에서 같은 실험을 반복했더니 이득이 **1.26배**로 줄었다(경계 아래 3.53배의 1/2.8).
출발점이 이미 bitmap(싼 쪽)이기 때문이다.

그리고 예측하지 않았던 게 하나 나왔다 — **어중간하게 뭉치면 오히려 손해다.**

| L (평균 run 길이) | 컨테이너 | 평균 nRuns | DV 샘플 | 범위 |
|---|---|---|---|---|
| 1 | bitmap | — | **463** | 415 ~ 566 |
| **8** | **run** | **849.9** | **686** | 668 ~ 713 |
| 64 | run | 106.5 | 649 | 585 ~ 676 |
| 512 | run | 14.0 | 546 | 524 ~ 561 |
| 4096 | run | 1.9 | **368** | 345 ~ 403 |

**L=8 이 L=1 보다 1.48배 비싸다** (범위 안 겹침). run 조회는 구간 배열의 이진 탐색이라
구간이 850개면 `log₂(850) ≈ 9.7` 단계인데, 8KB bitmap 은 1단계다.
L 을 더 키워 nRuns 가 한 자리로 떨어져야 비로소 bitmap 을 이긴다.

> **읽기와 저장이 반대로 가는 구간이 있다.** L=8 은 저장이 2.4배 좋아지는데
> (1,015,194 → 421,816 B) 읽기는 1.48배 나빠진다.

**조건 3 — 파일 스킵은 별개다.** 위 숫자는 술어를 뺀 조건이다. 실무에서는 정렬이
파일 스킵으로 더 큰 이득을 주지만 그건 DV 이야기가 아니다.

**조건 4 — 한 번 쓰고 300번 이상 읽을 때만** ([F-029](findings.md)).
이득만 재고 값을 안 재면 처방이 아니라 광고다. 그래서 정렬 쓰기 비용을 쟀다:

| | 쓰기 벽시계 | 저장 바이트 |
|---|---|---|
| 무정렬 | 20.07s (16.31–20.84) | 857,294,068 |
| **정렬** | **32.74s** (29.74–36.92) | **879,967,939** |

쓰기 **+63%**(행당 +1.58µs, 범위 안 겹침), 저장 **+2.6%**.

저장이 **커진 게 놀라웠다**(작아질 줄 알았다). 컬럼별로 쪼개니 기전이 정확했다:

| 컬럼 | 무정렬 | 정렬 | 배율 |
|---|---|---|---|
| **k04 (정렬 키)** | 10,051,608 | **25,151** | **0.003배** (399배 작아짐) |
| **id** | 8,173,850 | 16,879,442 | **2.065배** |
| **k13 (id 파생)** | 25,184,214 | 49,109,946 | **1.950배** |
| 나머지 17개 | — | — | 1.000배 (±0.1%) |

**정렬 키는 거의 공짜가 되고, 원래 순차적이던 컬럼이 그 값을 치른다.** 무정렬 테이블에서
`id` 는 파일 안에서 완벽한 등차수열이라 델타 인코딩이 극단적으로 잘 먹었는데, 재분배하면
그 이득이 날아간다. 나머지 17개가 **정확히 안 움직이는 것**이 통제가 살아 있다는 증거다.

> **실무 함의**: 삭제 키로 정렬하면 **원래 정렬돼 있던 컬럼(자동증가 id, 적재 타임스탬프)이
> 커진다.** 아무도 말해주지 않는 청구서다.

**본전 회수**: 스캔 1회당 0.042초 절감 vs 추가 쓰기 12.67초 = **약 300회**.
쓰기 비용도 스캔당 절감도 행 수에 비례하고 DV 절감은 투영 폭과 무관하므로,
이 300 은 우리 테이블 크기의 값이 아니라 **처방 자체의 값**에 가깝다.

즉 **일 단위 적재 + 하루 수백 회 조회하는 분석 테이블**이면 며칠 만에 회수되고,
**스트리밍 upsert 로 자주 다시 쓰는 테이블**이면 손해다.

### 8.3 처방을 한 문장으로

> **삭제가 적고(청크 밀도 6.25% 아래), 소수 키 값에 몰려 있고, 한 번 쓰고 수백 번 읽는
> 테이블이면 삭제 키로 정렬하라.** 삭제가 많으면 이득이 3분의 1로 줄고, 어중간하게 뭉치면
> 손해이며, 자주 다시 쓰는 테이블이면 쓰기 비용이 이득을 넘는다.

조건이 네 개나 붙는 처방이지만, **그 조건들이 전부 측정된 것**이라는 게 이 프로젝트가
내놓을 수 있는 최선이다. 조건 없이 "정렬하세요"라고 쓰는 편이 읽기는 좋지만 그건 광고다.

## 9. 기전 — 왜 비싼가

여기서부터가 이 프로젝트에서 가장 여러 번 틀린 부분이다.

### 9.1 8개월 동안 "PMU 가 없다"고 적어두고 확인을 안 했다

[F-001](findings.md) 은 4.1배의 **이유**를 이렇게 설명했다:
*"array 는 이진 탐색이라 분기 예측 실패가 많고, bitmap 은 분기가 없고 L1 에 상주한다."*
근거는 **비용 곡선의 모양뿐**이었다.

확증하려면 하드웨어 카운터가 필요한데, README·SETUP·findings 등 **8곳**에
*"WSL2 라 하드웨어 PMU 가 없다 → 확증은 AWS `.metal` 인스턴스에서"* 라고 적어뒀다.

2026-09-07 에 그냥 쳐봤다. **있었다.** WSL2 커널이 Hyper-V vPMU 를 노출하고 있었고
`branch-misses`, `cache-misses`, `cycles` 가 전부 값을 준다. 확인 명령은 README 에
이미 적혀 있었는데 `.metal` 에서 실행하라는 맥락으로만 적혀 있어서 로컬에서 칠 생각을
못 했다 ([F-028](findings.md)).

**통제군을 먼저 뒀다.** 가상화된 카운터는 이벤트가 뜨기만 하고 값이 0 인 경우가 있어서,
답을 아는 워크로드(고전적 sorted-vs-shuffled 분기 실험)로 먼저 확인했다:

| 통제군 | branch-misses | 실패율 | 벽시계 |
|---|---|---|---|
| SORTED (한 번만 뒤집힘) | 9,229,171 | 0.94% | 0.259s |
| SHUFFLED (동전 던지기) | **108,562,909** | **13.63%** | 0.681s |

이론값(2²⁰×200 의 절반 ≈ 1.05억)과 3% 안에서 맞는다. **카운터는 진짜로 센다.**

### 9.2 분기 예측도 캐시도 아니었다 — 명령어 수였다

`-prof perfnorm` 으로 마이크로벤치를 다시 쟀다 ([F-028](findings.md)):

| 패턴 | 컨테이너 | cycles/행 | **insn/행** | **분기실패/행** | IPC |
|---|---|---|---|---|---|
| 0.5% | array | 58.4 | 282.9 | 0.0126 | 4.84 |
| 5% | array | 78.8 | 370.0 | 0.0763 | 4.70 |
| **12%** | **bitmap** | **18.6** | **86.5** | 0.0292 | 4.66 |
| runs | run | 40.4 | 191.4 | 0.0066 | 4.74 |

- **분기 예측 실패는 비용 차이의 1.4% 만 설명한다.** 30만 사이클 격차를 설명하려면
  배치당 16,700회 더 틀려야 하는데 실제는 235회다. **두 자릿수가 모자란다.**
- **캐시 가설도 죽는다.** 가장 **빠른** bitmap 이 L1 미스는 **8배 많다**(1,173.9 vs 141.2).
- **IPC 가 4.66~4.84 로 사실상 상수**이고, 사이클이 명령어를 0.8~3.8% 안에서 따라간다.
  **파이프라인이 막혀서 비싼 게 아니라 그냥 일을 더 한다.**

**F-001 의 표는 그대로다**(4.1배는 이번에도 4.03배로 재현). 틀린 건 **"왜"** 다.

### 9.3 그리고 이게 처방을 강하게 만든다

행당 **86.5 명령어**. 이건 비트 하나 테스트하는 비용이 아니다. 가장 싼 경로조차
`contains(long)` 의 고정비(위치 쪼개기 → 키 배열 이진 탐색 → 2단 간접)를 다 낸다.

즉 **컨테이너 타입은 곁가지고, 진짜 비용은 "행마다 호출한다"는 구조 자체다.**
그리고 그게 정확히 §5.1 의 패치가 고치는 것이다 —
배치 API 로 바꾸면 이 고정비를 5,000번이 아니라 몇 번만 낸다.
**기전 설명이 처방과 같은 방향을 가리킨다.**

### 9.4 실제 쿼리 경로에서도 마찬가지다 — 그리고 `ctimer` 가 검증됐다

마이크로벤치를 실제 Spark 스캔으로 옮겼다 ([F-031](findings.md)):

| arm | cycles | instructions | branch-misses | 실패율 | IPC |
|---|---|---|---|---|---|
| baseline | 237,714,166,096 | 390,468,338,748 | 1,204,681,888 | 1.55% | 1.64 |
| patched | 203,636,206,746 | 260,507,995,090 | 1,200,937,204 | 2.51% | 1.28 |

- **분기 설명력 0.2%.** 가장 말해주는 건 절대값이 거의 같다는 것이다 —
  패치가 분기를 **38% 지웠는데** 실패 수는 안 줄었다.
  **지운 건 원래 잘 맞히던 분기였다.**
- **`ctimer` 50.00% vs `cycles` 52.21%, 차이 +2.21%p.**
  이 프로젝트가 지금까지 낸 **모든 비중 값이 사이클 기준으로도 같다.**
  43~58% 밴드가 샘플링 착시가 아니라는 뜻이고, 이건 F-008·F-011·F-020·F-027 전부를 떠받친다.
- 다만 **F-028 을 그대로 옮기면 안 된다.** 마이크로벤치는 명령어비와 사이클비가
  3.8% 안에서 맞았는데 실제 경로는 1.499배 vs 1.167배로 갈린다(IPC 1.64→1.28).
  **명령어를 절반 지워도 이득은 6분의 1만 온다.**
- 실제 스캔의 분기 실패율 **1.55%** 는 마이크로벤치(0.016%)의 **97배**다.
  마이크로벤치 카운터 값은 실제 경로로 못 옮긴다. 옮길 수 있는 건 결론뿐이다.

### 9.5 보정 0.53 의 정체는 JIT 이었다

[F-018](findings.md) 의 `wall = 0.53 × 샘플` 을 **다시 재지 않고** 이미 찍어둔
프로파일을 쪼갰다 ([F-033](findings.md)):

| 구간 | 전체 대비 |
|---|---|
| 스캔 (분석 대상) | 29.3% |
| **JIT 컴파일** | **41.6%** |
| Spark 실행 골격 | 10.6% |
| 클래스 로딩·검증 | 10.5% |
| 나머지 | 8.0% |

**프로세스 CPU 의 41.6% 가 JIT 컴파일이다.** 패치가 못 건드리는 고정비이고,
크기만 한 게 아니라 라운드마다 **31% 흔들린다.**

그런데 우리는 JVM 을 새로 띄워 **30회만** 돌린다. JIT 이 30회에만 상각된다.
프로덕션 익스큐터는 오래 살면서 수천 번 돈다. 그렇다면 0.53 은 **워크로드가 아니라
내 벤치 설계의 성질** 아닌가? 예측을 적고 `iters` 만 10배로 올려 쟀다:

| | iters=30 | iters=300 |
|---|---|---|
| 스캔 몫 | 29.3% | **47.4%** |
| JIT 몫 | 41.6% | **19.2%** |
| **희석 계수** | 계산 불가 (−0.26) | **0.447** |
| 라운드 간 퍼짐 | 31.1% | 15.2% |

**희석 계수 0.447 이 F-018 의 0.53 과 가깝다.** 보정의 정체는 **고정비 희석**이다.

> **함의**: `wall = 0.53 × 샘플` 은 **짧게 사는 JVM 의 성질**이다. 오래 사는 익스큐터에서는
> 희석이 약해지므로, **이 프로젝트가 보고한 벽시계 이득은 프로덕션에 대해 보수적**일
> 가능성이 높다. (다만 우리가 잰 건 여전히 단일 JVM 이므로 방향만 주장하고 크기는 주장하지 않는다.)

### 9.6 예외가 하나 있다 — 고삭제율의 반등

[F-008](findings.md) 의 bitmap 구간 반등(d=8%→50%, 1.26배)은 **다른 분기**의 이야기다.
F-028 이 반증한 건 *컨테이너 내부 이진 탐색*의 분기이고, 여기는
`if (!contains(pos))` 라는 **데이터 의존 분기**로 d=50% 에서 정확히 동전 던지기가 된다.

기대값을 **먼저 계산**해 예측을 반증 가능하게 만들었다(2.64억 행 × 42%p ≈ 1.11억 회
추가 실패, 총량의 9%). 결과 ([F-032](findings.md)):

- 총 branch-misses **+7.9%** (범위 안 겹침, 계산한 기대값 9% 와 근접) ✅
- DV 구간 절대 실패 8,271만 → **1억 1,551만 (+40%)**, 범위 안 겹침 ✅
- 그러나 늘어난 DV 사이클의 **28.5% 만** 설명한다 ❌

| 축 | 분기 예측 실패의 설명력 |
|---|---|
| F-028 컨테이너 비용 차이 (마이크로벤치) | 1.4% |
| F-031 패치 전후 (실제 경로) | 0.2% |
| **F-032 고삭제율 반등** | **28.5%** |

**세 축 중 여기서만 분기가 의미 있는 몫을 갖는다.** 20배 차이다.

나머지도 **재측정 없이** 좁혔다 ([F-034](findings.md)). 프레임별로 빼보니:

| 말단 프레임 | 절대차 | 순증 대비 |
|---|---|---|
| **`ColumnarBatchUtil.buildRowIdMapping`** | **+10,176** | **+206%** |
| `RoaringBitmap.contains` | +1,075 | +22% |
| **`DeleteCounter.increment`** | **+858** | **+17%** |
| **`Util.hybridUnsignedBinarySearch`** | **−4,160** | **−84%** |

**조회 기계장치는 오히려 싸진다**(이진 탐색이 거의 사라진다). **루프 몸통이 비싸져서**
순증이 된다. 몸통 안에서 이름이 붙은 것: 분기 28.5% + `DeleteCounter.increment` 17%
(삭제 행마다 1회, d=50% 면 400만 회) = **약 45%**. **나머지 55% 는 아직 모른다.**

#### 그 55% 에 이름을 붙였다 — 새 범인이 아니라 **같은 분기**였다

루프 몸통은 Spark 경로에서 뜯을 수 없으므로 변형 6종을 만들어 `ns/op` 로 다시 쳤다
([F-037](findings.md)). 프레임 귀속은 JIT 인라이닝에 흔들리지만 `ns/op` 는 면역이다.

| 변형 | 남긴 것 | d=8% | d=50% | 증가폭 |
|---|---|---|---|---|
| **v1_full** (현행) | 분기 O · 저장 O(`live`) | 28.880 | 37.296 | **+29.1%** |
| **v4_branchless** | 분기 X · 저장 O(`live`) | 28.024 | 27.903 | **−0.4%** |
| v5_lookupOnly | 분기 X · 저장 X | 27.060 | 21.779 | −19.5% |

**분기를 지우면 반등이 100% 사라진다.** 그런데 오예측 페널티로 세지는 몫은
(+680회 × 18사이클) / +37,185사이클 = **33%** 뿐이다. 나머지는 어디 있나 —

| | d=8% | d=50% |
|---|---|---|
| 명령어/op | 587,777 | 604,491 (**+2.8%**) |
| IPC | 4.62 | **3.68** (−20.3%) |

**일이 늘어서가 아니라 파이프라인이 막혀서다.** 예측 불가능한 분기는 투기 실행을 끊어
루프를 직렬화하고, 그 정지는 `branch-misses` 가 아니라 IPC 로만 보인다.
**미상 55% 는 F-032 의 28.5% 와 같은 분기였고, 카운터가 3분의 1만 세고 있었다.**

> ⚠️ 변형 6개 중 **둘은 설계 실수**였다. `v2_noStore` 는 저장을 없애자 JIT 이 조건문을
> 산술로 바꿔(분기 실패 1,084 → 4.1) '분기 유지' 대조군이 못 됐고, `v6_withCounter` 는
> 카운터를 넣으면서 `if` 를 `if/else` 로 같이 바꿨다.
> 하드웨어 카운터를 함께 안 찍었으면 **"저장이 범인"이라는 반대 결론**을 냈을 것이다.

`mapping[live++]` 주소 의존 가설(v3)은 **살지도 죽지도 않았다** — v3 은 증가폭이 39%로
줄었지만 분기 실패도 69%로 같이 줄어서, 변형 하나가 두 가지를 바꿨다.

## 10. 내가 틀린 것들

이 장이 이 프로젝트에서 가장 중요하다. 규율이 없었다면 아래 대부분이 **발견으로
발표됐을 것**이기 때문이다.

### 10.1 반복 측정이 단일 측정본을 뒤집은 것

| 무엇 | 단일 측정본의 결론 | 3회 반복 후 |
|---|---|---|
| bitmap 구간 | "평평하다, 차이는 노이즈" | **틀렸다.** 1.26배 반등이 있다 ([F-008](findings.md)) |
| 클러스터링 곡선 | "nRuns 가 줄면 단조 감소" | **틀렸다.** L=1,2,4,8 은 서로 구분되지 않는다 ([F-009](findings.md)) |
| `√n` 노이즈 추정 | 반복 횟수로 추정 | **완전히 틀렸다.** 실측 9.7% ([F-010](findings.md)) |

### 10.2 예측이 빗나간 것들 (선기록했으므로 숨길 수 없었다)

  뒤집혀서 철회**했다.
- **F-025 의 "s24 이상치"** → **존재하지 않았다.** 집계에 **평균**을 썼고 3라운드가
  오염돼 있었다(s16 1.76배, s32 1.42배, s8 1.29배가 같이 튀고 s24 만 멀쩡).
  중앙값으로 다시 적합하면 R² 0.892 → 0.950, 잔차 −6.0% 로 노이즈 안이다
  ([F-030](findings.md)). **없는 현상을 후속 과제로 남겨둘 뻔했다.**
  원인은 **규칙이 도구마다 달랐던 것** — 다른 채점기는 중앙값인데 `strlen.py` 만 평균이었다.
- **F-001 의 기전 설명** → 분기도 캐시도 아니었다 ([F-028](findings.md)).
- **"WSL2 에는 PMU 가 없다"** (8곳) → 있었다 ([F-028](findings.md)).

  d=6.10% 는 array 쪽 정점이고 반등은 d=8%→50% 다. 채점에서 빼고 다시 쳤다
  ([F-031](findings.md)).
- **F-015 의 "d=6.1% 6/6 저하"** → **우연이었다.** 쌍을 18개로 늘리니 신규 12쌍이

  무조건 "유의" 로 보인다 ([F-038](findings.md)).
- **Q_P8 채점** → DV 비중(스캔 서브트리 기준)에 `perf stat` 총량(프로세스 전체 기준)을
  곱해 **"총 추가 실패의 183.9%"** 라는 말이 안 되는 값을 냈고 **그 상태로 "맞음"
  판정이 났다.** 분모를 맞추니 34.9% 이고 판정이 "절반만 맞음"으로 뒤집혔다
  ([F-032](findings.md)).

### 10.4 같은 함정을 반복해서 밟은 것

**`config.env` 오버라이드 함정 — 일곱 번.** 두 변종이 있다:

- **변종 A**: config 가 `VAR=값` 으로 **하드코딩**하면 `VAR=x ./script` 가 조용히 무시된다.
  (`REPS`, `WIDE_COLS`, `DENSITIES_BP`, `ROWS_PER_FILE`)
- **변종 B**: config 가 이미 값을 채운 뒤에 스크립트가 `VAR="${VAR:-내기본값}"` 을 쓰면
  **내 기본값이 죽은 코드**가 된다. (`REPS`, `SCAN_ITERS` ×3)

가장 아팠던 건 일곱 번째다. [F-033](findings.md) 의 축은 **`iters` 를 30→300 으로
올리는 게 측정의 전부**인데 30 으로 돌았다. 알아챈 단서는 숫자가 **안 움직인 것** —
10배 일했다는데 전체 샘플이 573,119 → 501,259 로 **오히려 줄었다.**

**게이트가 산출물이 아니라 로그를 본 것 — 세 번.**
- `gen_*.json` 영수증이 커밋돼 있어서 **빈 warehouse 를 향해** 측정이 시작됐다.
- `grep -q "master=spark://"` 가 통과했는데 **24개 실행이 아무것도 안 만들었다.**
- `grep -E "median="` 이 spark-submit 에러를 삼켰다.

**`scan.py` 가 `--master` 를 덮어썼다.** 클러스터로 던진 잡이 마스터 노드에서
조용히 `local[4]` 로 돌았다. **결과는 멀쩡히 나왔고 에러도 없었다.** 유일한 단서는
워커의 빈 `work` 디렉터리와 프로파일 0개였다.

**전제를 검증 안 했다.** "환경 때문에 못 한다"를 8곳에 적고 8개월 뒤 되는 걸 발견했다.
예측을 선기록하는 규율은 있었는데 **전제를 선검증하는 규율이 없었다.**

**그 외**: Iceberg 매니페스트에 로컬 절대경로가 박혀 워커가 파일을 못 찾은 것
(그리고 **내 첫 진단(S3A 클래스로더)이 틀렸다는 것**), 28개 셸 스크립트에 exec 비트가
없었는데 WSL DrvFs 가 0777 로 보고해서 로컬에서는 안 보였던 것, `ctimer` 지원 확인이
`java -version` 으로 프로브해서 **거짓 음성**이 뜬 것, Git Bash → WSL 에서 `$VAR` 가
작은따옴표 안인데도 바깥에서 먼저 치환돼 **에러 없이 빈 값으로 돌던 것**.

## 11. 최종 결론

### 11.1 이 문제가 당신에게 해당되는가

**해당된다면:**
- Iceberg **V3** 테이블을 **merge-on-read** 로 쓰고 있고,
- **좁은 투영**(몇 컬럼만 SELECT)이 많고,
- 삭제율이 **청크 밀도 0~6.25% 구간**(= 대부분의 CDC 워크로드)이고,
- 쿼리가 스캔 위주다(무거운 집계가 없다).

**판정 기준 하나로 줄이면**: **DV 체크가 스캔 CPU 의 20% 이상**이면 이 패치가
벽시계로 보인다. 그 밑이면 CPU 는 줄어도 쿼리 시간은 안 변한다.

### 11.2 무엇을 발견했는가

1. **행 단위 프로브가 좁은 스캔에서 스캔 CPU 의 43~58% 를 차지한다.**
   이 밴드는 CPU 3종·스토리지 2종·병렬도 16배·셔플·분산 클러스터에서 유지된다.
   (분산 클러스터에서는 42% 로 내려앉고, 그게 하한이다.)
2. **구간 API 로 바꾸면 최악 지점에서 9.28배, `_deleted` 경로에서 18.9배** 싸진다.
   equality delete 경로는 회귀가 없다.
3. **비용의 정체는 분기 예측도 캐시도 아니고 "행마다 호출한다"는 구조**다.
   가장 싼 컨테이너조차 행당 86.5 명령어를 쓴다.
4. **삭제율 6.25% 부근에서 비용이 불연속적으로 점프**하고, 그 **아래 구간 전체**가
   행당 비용이 가장 비싼 영역이다. 직관과 반대다.
5. **오늘 할 수 있는 처방**: 삭제 키로 정렬하면 DV 체크가 2.80배(패치까지 하면 12.39배)
   싸진다. 단 **조건 세 개** — 삭제가 소수 키 값에 몰릴 것, 파일 스킵과는 별개, 그리고
   **한 번 쓰고 300번 이상 읽을 것**(쓰기 +63%, 저장 +2.6%).

### 11.3 이 프로젝트가 방법론으로 남기는 것

숫자보다 이게 더 오래 갈 것 같다:

- **예측을 먼저 적어라.** 이 프로젝트는 예측이 **15번 빗나갔고**, 그때마다 배웠다.
  적어두지 않았다면 전부 "예상대로였다"가 됐을 것이다.
- **노이즈를 먼저 재라.** 9.7% 를 모른 채였다면 반등도 클러스터링 곡선도 잘못 읽었다.
- **전제도 측정 대상이다.** "환경 때문에 못 한다"를 8곳에 적고 8개월을 버렸다.
- **게이트는 산출물을 봐라.** "✅ 완료 (0초)"는 거짓말을 한다.
- **100% 를 넘는 비율이 나오면 멈춰라.** 분모가 섞였다는 뜻이다.
- **숫자가 안 움직이면 의심해라.** 10배 일했는데 샘플이 줄면 설정이 안 먹은 것이다.

- 테이블 모양이 하나다: 8M 행 / 4파일 / 20컬럼. 파일 수천 개, 중첩 타입, 술어 있는
  스캔은 안 쟀다.
- 벤치는 JDK 21, Spark 측정은 JDK 17 이다 (서로 다른 축이므로 섞어 읽으면 안 된다).

**방법론의 한계**
- `ctimer` / `cycles` 는 **inclusive 샘플링**이다. 스택에 DV 프레임이 있으면 그 샘플
  전체를 DV 로 센다. 배타적 자기 시간이 아니다.
- 프로파일 비중과 벽시계 사이에는 **고정비 희석**이 있다 (보정 ≈ 0.45~0.53).
  그 정체가 JIT 이라는 것까지는 밝혔지만 ([F-033](findings.md)), 남은 부분은 미상이다.
- 클러스터링 축(`C`)과 `p` 축은 **술어를 조작한 합성 축**이다. 실제 정렬은 F-023/F-026 이
  따로 쟀다.

**🟡 측정했지만 주장하지 못하는 것**
- 반등의 DV 사이클 증가(+15.5%) — 범위가 겹친다.
- d=6.1% 의 patched 6/6 저하 — 일관적이지만 기전 미상.
- 셔플 축의 예측 효과 — 노이즈 바닥 밑.

# 0) 환경
